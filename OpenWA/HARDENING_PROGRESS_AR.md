# تقدم تجهيز OpenWA

12 أكتوبر 2026 — هذه تغييرات محلية، وليست إعلان تشغيل إنتاج.

تم فرض ADMIN على إدارة البنية والإضافات، وفحص قيود الجلسة وIP عند الاشتراك في WebSocket، وإعادة التحقق قبل بث أحداث الجلسة لرفض المفاتيح الملغاة. أحداث إدارة Webhooks مقيدة بالمدير غير المقيد بجلسات. HTTP لم يعد يثق مباشرة في X-Forwarded-For؛ خلف proxy يلزم إعداد trust proxy محدد قبل الاعتماد على قائمة IP خارجية.

تم ضبط أولوية process env، وتشغيل صورة Docker بالمستخدم openwa، وإزالة docker.sock. التشغيل على volume قديمة يحتاج التأكد من ملكية الملفات للمستخدم قبل البدء؛ لم نغير ملفات الجلسات الحالية.

تم تثبيت الاعتماديات مجدداً وتحديث lockfile بتحديثات npm audit المتوافقة، وإصلاح بناء اللوحة باستبدال ثلاثة أصول مفقودة بأيقونات من lucide. التثبيت المحلي استخدم ignore-scripts، لذلك نجاح البناء والوحدات لا يثبت عمل SQLite native أو Chromium في runtime.

نجح بناء API واللوحة. فحص اعتماديات الإنتاج بعد التحديث سجل 11 نتيجة high وصفر critical؛ لا نعتبره خالياً من الثغرات. لا نستخدم audit fix --force لأنه يقترح تغيير إصدار محرك WhatsApp دون اختبار توافق.

## إعداد الشبكة الداخلية

ملف docker-compose.internal.yml يستخدم مع الملف الأساسي وprofile postgres، ولا يستخدم docker-compose.staging.yml. لا يفتح منفذ API على المضيف. يتطلب API_MASTER_KEY وDATABASE_PASSWORD وOPENWA_BACKEND_NETWORK. شبكة Docker الخارجية المحددة يجب أن تكون موجودة وأن ينضم إليها عامل الدعوات المصرح، بينما تظل قاعدة OpenWA على شبكة compose الخاصة.

للتحقق البنيوي فقط، بعد إعداد المتغيرات في بيئة آمنة:

```sh
docker compose -f docker-compose.yml -f docker-compose.internal.yml --profile postgres config --quiet
```

نجح هذا التحقق بمتغيرات وهمية؛ لم تبدأ الحاويات. لا تُستخدم المتغيرات الوهمية للتشغيل. لا تُنسخ .env أو data إلى الصورة؛ .dockerignore يستبعدهما.

## المتبقي قبل الإنتاج

- إصلاح SSRF وحدود الوسائط وحماية Webhook queue UI عند تفعيلها.
- Queue دائمة ومحاولات ثابتة مع unknown؛ bulk الحالي غير معتمد للإنتاج.
- ربط منصة الدعوات، وصلاحيات الاتصال لكل مساحة وسجل التسليم.
- معالجة نتائج audit المتبقية مع اختبار توافق محرك WhatsApp.
- اختبارات runtime مع Node 22 وSQLite native وPostgres وmigrations واستعادة backup، ثم ربط رقم اختبار بواسطة صاحبه.
- استبدال e2e الحالي: ما زال يتوقع Hello World ويحمّل AppModule كاملاً؛ لم يُشغّل لأنه قد يصل إلى البيانات والجلسات الافتراضية. يلزم isolation قبل تشغيله.

الخطة التفصيلية في ../docs/OPENWA_IMPLEMENTATION_PLAN_AR.md. تقرير الجاهزية السابق يمثل حالة الكود قبل هذه الإصلاحات؛ لا ينبغي قراءة نتائجه كأن كل بند ما زال دون تغيير.

## تحديث الربط — 12 أكتوبر 2026

نُفذ ربط خلفي وواجهة في منصة الدعوات، مع طابور PostgreSQL وصلاحيات منفصلة وWebhooks موقعة. أضيف callback لتصدير message.ack من SessionService. لا يعتمد الربط على bulk الحالي ولا يرسل ملفات أو يسمح بعناوين مزود من العميل. تفاصيل التشغيل في [دليل الربط](../docs/WHATSAPP_INTEGRATION_AR.md). لا توجد رسالة WhatsApp فعلية مرسلة ضمن اختبارات التنفيذ، والتفعيل الإنتاجي يحتاج نشر المكونات وربط الرقم.

## النشر الفعلي

نُشرت الخدمة داخل الشبكة الخاصة مع PostgreSQL مستقل، والخادم والواجهة وعامل WhatsApp. صححت تهيئة الجلسة كي لا تستبدل QR_READY/READY بحالة INITIALIZING عند عودة initialize. نجح اختبار QR حقيقي دون ربط هاتف؛ اختبارات الوحدة 116 ناجحة. أضيفت حماية موارد الخدمة ومراقبة العامل ونسخ OpenWA إلى النسخ المجدول، مع تجربة استعادة ناجحة. التفاصيل في [دليل الربط](../docs/WHATSAPP_INTEGRATION_AR.md) و[أدلة النشر](../docs/WHATSAPP_DEPLOYMENT.json).

### إصلاح QR القديمة أثناء الربط — 12 أكتوبر 2026

أضيفت مهلة عرض 15 ثانية للـQR المحفوظة؛ لا يرجع adapter الصورة أثناء المصادقة أو الانقطاع، أو بعد مرور المهلة دون QR event جديدة. اختبارات الخدمة 120 ناجحة. واجهة دعوة تتابع الحالة والصورة أثناء المحاولة، وتمسح الصورة عند انتهاء العرض أو تعذر الوصول أو الانتقال إلى المصادقة، وتنتظر تجديدها في فترات توقف المحرك. اختبارات الواجهة 18 ناجحة. نُشر الإصلاح وفُحص توليد QR ورفض النسخة القديمة على الخدمة الحية، دون إرسال رسائل أو ربط هاتف اختباري.

### إصلاح معرّفات المحادثة وإيصالات الإرسال — 13 أكتوبر 2026

أصبح resolveChatId يتحقق من رقم الهاتف حتى عند تقديم @c.us، ويستخدم معرّف @lid الذي يرجعه WhatsApp عند وجوده. غياب معرّف الرسالة لا ينتج معرّف نجاح اصطناعياً ولا محاولة إرسال ثانية. أضيف waitUntilMsgSent مع sendSeen=false للنص والصورة. نجحت 128 حالة وحدة. لوحظت المشكلة في الفحص الحي عبر lookup للرقم وقراءة المحادثة دون تنفيذ إرسال، وأكد صاحب الطلب عدم وصول صورتيه. التفاصيل وأدلة النشر في دليل ربط المنصة.

نُشر إصلاح LID في openwa-api:whatsapp-20261013. أعيد تشغيل API مع volume الجلسات القائمة، وعاد الرقم متصلاً دون QR جديدة. حزمة adapter المترجمة مطابقة للبناء المحلي المختبر. لم يُنفذ إرسال تجريبي ضمن النشر.

### توافق MediaData وMsgKey — 13 أكتوبر 2026

كشف اختبار واحد مأذون به أن إصلاح LID لم يعالج خطأ تركيب الصورة بالكامل. أضاف SDK حالة MediaData الداخلية إلى Msg، ففقد النموذج id أثناء البناء قبل البث. أضيف wwjs-browser-compatibility.ts لتحويل الوسائط إلى خصائص المخطط واستبعاد الهوية والحالة الداخلية، ولربط MsgKey.toString بمعرّفات الإيصالات التي يتوقعها SDK القديم. تهيأ الدوال عند readiness وقبل الإرسال دون تغليف متكرر، ولا تصدر callbacks لمعرّف ACK مفقود.

نجحت 134 حالة وحدة وبناء API. أعيد إنتاج الخطأ بالصورة الحالية مع حجب عمليات الإضافة والحفظ والبث؛ اجتاز التصحيح البناء حتى حاجز حفظ الرسالة. لا يُعد ذلك اختبار تسليم فعلي بعد الإصلاح، ولم تكرر محاولة الإرسال المأذون بها. التفاصيل في دليل الربط وأدلة النشر.
