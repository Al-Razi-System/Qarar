# Qarar engineering constitution

These instructions apply to every file in this repository. More specific `AGENTS.md`
files may add framework instructions, but may not weaken these rules.

## Required reading before changing behavior

Before editing a business process, read:

1. `docs/engineering/CHANGE_SAFETY_POLICY_AR.md`
2. `docs/engineering/CHANGE_IMPACT_TEMPLATE_AR.md`
3. `docs/architecture/IDENTIFIER_STANDARD_AR.md` when creating or changing entities
4. `docs/architecture/DOMAIN_STATE_MACHINES_AR.md` for lifecycle changes
5. `docs/testing/CRITICAL_E2E_SCENARIOS_AR.md` for the affected journey
6. `docs/testing/COMPREHENSIVE_TEST_PROGRAM_AR.md` for test scope and release gates

For dashboard work, also obey `apps/dashboard/AGENTS.md` and read the relevant
Next.js documentation shipped in `apps/dashboard/node_modules/next/dist/docs/`.

Before building or changing any screen, read `docs/design/DESIGN_STANDARDS_AR.md`.
Colours, type sizes and radii come from the tokens in `apps/dashboard/src/app/globals.css`
and screens are composed from `apps/dashboard/src/shared/ui`; never hand-write a colour
or a font size inside a screen.

## Non-negotiable change protocol

No behavior change may start with code. First record an impact map in the task notes,
PR description, or commit context covering:

- user journey and business invariant;
- callers, consumers, API/RPC contracts, tables, triggers, jobs, UI surfaces and roles;
- state before the action, permitted transition, state after it and rollback/failure state;
- existing records and migrations affected;
- tests that reproduce the defect and protect adjacent stages.

If any item is unknown, inspect it before editing. Never guess a database contract,
permission boundary, role, state value, or framework API.

## Definition of done

A change is incomplete unless all of the following are true:

- the root cause is fixed, not only one damaged record or visible symptom;
- a failing regression test exists first, or the task explicitly documents why an
  automated test is impossible and provides a repeatable verification procedure;
- the changed stage and its immediately preceding and following stages are tested;
- authorization is tested for allowed and denied contextual roles;
- loading, success, validation, conflict and server-failure states are visible at
  the action location; rejected promises and silent failures are forbidden;
- API/RPC errors preserve a traceable internal cause while returning safe Arabic UI copy;
- old data and in-flight processes remain valid or receive an explicit repair migration;
- lint, typecheck, focused tests and applicable contract/integration tests pass.

## Database and migration rules

- Never edit a migration that may have run in any shared environment. Add a new
  forward-only corrective migration.
- Multi-record lifecycle transitions must be atomic and concurrency-safe.
- Critical invariants belong in database constraints, triggers, or transactional RPCs;
  UI checks alone are insufficient.
- Schema/RPC changes require a repository-wide consumer search and contract tests.
- Data repair must be idempotent, scoped, auditable and separated from demo seeding.
- Never test destructive migrations against production data first.

## State, permissions and identity rules

- State values are controlled domain contracts, not arbitrary strings.
- Every transition has actor, preconditions, effects, failure behavior and audit event.
- Permissions are evaluated in the resource context. A global permission does not imply
  chair, rapporteur, member, submitter, reviewer or assignee authority.
- Internal primary keys are immutable UUIDs. Human references are generated by the
  server/database from the entity type and are never requested from users.

## UI and error rules

- Do not present an enabled action the backend will predictably reject.
- Disabled actions explain the exact unmet requirement beside the action.
- Never expose enum names, raw SQL/API errors or English machine statuses to users.
- A mutation must have in-place pending, success and failure feedback and prevent unsafe
  double submission.
- Responsive behavior is part of acceptance; sidebars, dialogs and tables must be checked
  at desktop and narrow widths.

## Release safety

- Use local development with hot reload for iteration and an isolated development database.
- Validate integrated journeys on staging. Production is for a tested release batch, not
  interactive debugging or hot reload.
- Do not deploy while mandatory checks fail or migration/source drift exists.
- Preserve unrelated user changes in a dirty worktree.

Run `npm run test:development-governance` before handing off any repository-wide change.
