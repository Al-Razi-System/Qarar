# دليل احتواء مصدر سلطة IAM

هذا الدليل يضبط تشغيل الترحيل
`20260816080000_iam_authority_provenance_boundary.sql`. الغرض منه منع تحول دور
محلي ظاهريًا إلى دور واسع النفوذ عبر تغيير مصفوفة الصلاحيات، أو عبر دعوة أو SSO أو
تفويض. الترحيل **مقصود أن يفشل** إذا وجد إعداد تاريخي قد يمنح تلك السلطة؛ لا تتجاوز
الفشل بحذف القيود أو بالتعديل المباشر في قاعدة إنتاج.

## قاعدة مصدر السلطة

لا يكفي اسم الدور أو `role_scope` وحده لتحديد خطورته. يعد الدور مرتفعًا إذا كان
نطاقه المعلن `organization` أو `system`، أو إذا كان يحمل صلاحية فعّالة نطاقها أحد
هذين المستويين. لذلك يطبق الحاجز التالي على الدور والصلاحية والعضوية والدعوة وSSO
والتفويض، بما في ذلك تعديل السجل مباشرة من مسار إداري.

| نطاق الصلاحية | نطاقات الدور المسموحة بهذا الحاجز | هل يعد الدور مرتفعًا؟ | من يدير/يمنح/يلغي السلطة المرتفعة؟ |
| --- | --- | --- | --- |
| `system` | `system` فقط | نعم | مدير نظام فقط |
| `organization` | `organization` أو `system` | نعم | مدير نظام فقط |
| `governance_unit` | جميع نطاقات الأدوار الحالية | لا بمفرده | قواعد الوحدة وصلاحيات API العادية |
| `execution` | جميع نطاقات الأدوار الحالية | لا بمفرده | قواعد التنفيذ وصلاحيات API العادية |
| `self` | جميع نطاقات الأدوار الحالية | لا بمفرده | قواعد الحساب وصلاحيات API العادية |

هذه مصفوفة منع **ترقية النطاق** وليست بديلاً عن `has_permission` أو RLS أو شرط
الوحدة المستهدفة. على سبيل المثال، وجود صلاحية `governance_unit` لا يفتح وحدة أخرى
ولا يمنح إذنًا أعلى. تغيير أي دور أو صلاحية مرتفعة، أو منحها أو سحبها من عضوية، يجب
أن يمر بمدير نظام فعلي وبالمسار الإداري المعتمد.

## الدعوات وSSO

- لا يجوز أن تحمل دعوة بحالة `pending` دورًا مرتفعًا. أرسل دعوة بلا دور أو بدور غير
  مرتفع، ثم بعد أن تصبح الهوية مفعلة ومتحققًا منها يعيّن مدير النظام الدور المرتفع من
  مسار التعيين العادي.
- لا يجوز لـ`default_role_id` في مزود SSO ولا لخريطة مجموعة SSO فعّالة أن تمنح دورًا
  مرتفعًا، حتى لو كانت المجموعة صادرة من IdP موثوق. SSO يثبت الهوية والمجموعة؛ لا
  يصبح مصدرًا تلقائيًا لسلطة المؤسسة أو النظام.
- يبقى `sync_current_sso_groups` خدمة داخلية فقط ومشروطًا بادعاء IdP متحقق. لا تمرر
  المجموعات من المتصفح أو تطبيق العميل. بعد الترحيل لا تستخدم المزامنة لمنح دور
  مرتفع؛ عيّنه مدير النظام بعد التحقق من الهوية.
- لا تعِد تشغيل SSO لمجرد اجتياز هذا الفحص. يظل تحقق ملكية النطاق وسلامة assertion
  وإجراء enable الموثق شروطًا مستقلة.

## التفويض

التفويض ينسخ السلطة الفعالة لعضوية مصدر محددة ضمن الفترة الزمنية، ولا ينشئ دورًا
جديدًا. عند إنشاء تفويض:

- يكون المصدر عضوية نشطة في المؤسسة الحالية، والهدف مستخدمًا نشطًا في المؤسسة نفسها.
- لا ينشئه إلا صاحب عضوية المصدر مع `iam.roles.assign` في الوحدة المعنية أو مدير
  النظام؛ أما تفويض الدور المرتفع فلا ينشئه إلا مدير نظام.
- الحد الأقصى 90 يومًا، والتداخل النشط لنفس المصدر والهدف مرفوض.
- يسجل الأثر التدقيقي `actor_user_id` للفاعل الحقيقي، إضافة إلى المستخدم المصدر
  والهدف والدور؛ لا تفترض أن صاحب عضوية المصدر هو من نفذ العملية.
- إلغاء تفويض مرتفع محصور بمدير النظام. أما التفويض غير المرتفع فيتطلب
  `iam.roles.revoke` في وحدة المصدر.

لا تمنح صلاحية محلية لشخص أن يختار عضوية مصدر لشخص آخر أو أن يرفع تفويضًا محليًا
إلى سلطة مؤسسة بسبب تعديل لاحق في مصفوفة الأدوار.

## فحص قبلي إلزامي

نفذ الفحص في نسخة معزولة مطابقة للإنتاج أولًا، ثم من اتصال تشغيلي مقيد بالقراءة إلى
الإنتاج داخل نافذة التغيير. الملف
[`supabase/scripts/iam-authority-provenance-preflight.sql`](../supabase/scripts/iam-authority-provenance-preflight.sql)
يعمل داخل معاملة `READ ONLY` وينهيها بـ`ROLLBACK`؛ لا ينفذ أي `INSERT` أو `UPDATE`
أو `DELETE`.

استخدم اتصالًا صادرًا من مخزن الأسرار أو إعداد `PGSERVICE` محميًا، ولا تضع رابط
قاعدة البيانات أو كلمة المرور في سطر الأوامر أو سجل الطرفية:

```sh
psql -X -v ON_ERROR_STOP=1 \
  -f supabase/scripts/iam-authority-provenance-preflight.sql
```

يجب أن تكون نتيجة `summary` الوحيدة هي `{"blocking_rows": 0, "ready": true}`.
أي صف إضافي هو **No-Go** للترحيل. نفذ الفحص مرة بعد الإصلاح ومرة أخيرة مباشرة قبل
التطبيق؛ يعيد الترحيل نفسه التحقق دفاعًا من أي تغيير حدث بين الفحص والتطبيق.

| نتيجة الفحص | الإصلاح المعتمد قبل الترحيل |
| --- | --- |
| `role_permission_scope_mismatch` | أزل/عطّل منح الصلاحية المخالف عبر طلب تغيير مصفوفة ومراجعة مستقلة، أو ارفع نطاق الدور بعد اعتماد مدير النظام. راجع كل عضوية موجودة للدور قبل اختيار رفع النطاق. |
| `pending_elevated_invitation` | ألغِ الدعوة وأعد إصدارها بلا دور أو بدور غير مرتفع. بعد تفعيل هوية المدعو، يعيّن مدير النظام الدور المرتفع صراحة. |
| `elevated_sso_default_role` | أزل الدور الافتراضي أو استبدله بدور غير مرتفع؛ لا تستبدله بمجموعات SSO مرتفعة. |
| `active_elevated_sso_group_mapping` | عطّل/أزل الخريطة، ثم راجع العضويات المشتقة منها وسحب الوصول الزائد قبل إعادة مزامنة SSO. |
| `active_elevated_delegation` | ألغِ التفويض النشط، واحفظ سبب العمل وسجل التدقيق. إن بقيت الحاجة، يعيد مدير النظام فقط إنشاء تفويض جديد ضمن المدة المصرح بها. |
| `delegation_source_organization_mismatch` | أوقف السجل عن منح أي وصول، ثم عالجه بترحيل تصحيحي معتمد أو بإلغاء التفويض وإعادة إنشائه بمصدر عضوية من المؤسسة نفسها. لا تنقل عضوية مصدر بين المؤسسات لتجاوز الفحص. |

لا تعدل صفوف `qarar_iam` يدويًا لتجعل الفحص أخضر. استخدم عقود الإدارة ومراجعة
التغييرات، أو ترحيلًا تصحيحيًا أماميًا معتمدًا ومجربًا على نسخة معزولة. احتفظ بتقرير
الفحص وتذكرة الاعتماد ونتيجة مراجعة العضويات ضمن دليل الإصدار.

## التحقق بعد التطبيق

1. شغّل اختبارات الترحيل وعقود IAM على بيئة معزولة، بما فيها اختبار حدود مصدر
   السلطة، قبل فتح الحركة.
2. شغّل `npm run prod:permissions-audit` و`npm run prod:migration-drift` واحفظ
   النتائج خارج Git.
3. راجع سجل التدقيق لعمليات `iam.delegation.create` و`iam.delegation.revoke` وتحقق
   من تطابق الفاعل الحقيقي مع تذكرة التغيير.
4. اختبر سلبيًا أن دعوة أو SSO default أو SSO group mapping لدور مرتفع ترفض، وأن
   مدير وحدة لا يستطيع إنشاء أو إلغاء تفويض مرتفع.

أي فشل بعد التطبيق يعالج بـforward-fix أو بخطة استعادة معتمدة؛ لا تعكس ترحيل IAM
بشكل يدوي في الإنتاج.
