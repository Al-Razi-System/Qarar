# دليل GitFlow المبسط لمشروع Qarar

## 1. الهدف

يوضح هذا الدليل طريقة العمل المعتمدة داخل مستودع `Qarar` لإدارة الفروع، والدمج، والمراجعة، والتسليم، بشكل موحد مع المشاريع الأخرى قدر الإمكان، وخصوصاً `Da3wa-Platform`.

يعتمد `Qarar` على:

- `GitFlow` مبسط لإدارة الفروع والدمج
- `GitHub Projects` لإدارة العمل
- `Scrumban` لإدارة التدفق التنفيذي اليومي

---

## 2. الفروع الأساسية

### 2.1 فرع `main`

- مخصص للإصدارات المستقرة فقط
- يمنع العمل المباشر عليه
- لا يتم الدمج إليه إلا بعد اكتمال المراجعة والاختبار وجاهزية الإصدار

### 2.2 فرع `dev`

- هو فرع التطوير الرئيسي
- جميع الميزات والإصلاحات والتحديثات التوثيقية تدمج إليه أولاً
- يمنع التعديل المباشر عليه

---

## 3. فروع العمل

### 3.1 فروع `feature`

تستخدم لتنفيذ الميزات أو المهام الجديدة، ويجب أن تبدأ من `dev`.

الصيغة:

```text
feature/short-task-name
```

أمثلة:

```text
feature/pb-023-ai-minutes-draft
feature/pb-053-flutter-app-shell
feature/pb-054-supabase-core-schema
```

### 3.2 فروع `bugfix`

تستخدم لإصلاح الأخطاء، ويجب أن تبدأ من `dev`.

الصيغة:

```text
bugfix/short-bug-name
```

أمثلة:

```text
bugfix/pb-019-voting-eligibility
bugfix/fix-meeting-status-transition
```

### 3.3 فروع `docs`

تستخدم للتحديثات التوثيقية عند الحاجة.

الصيغة:

```text
docs/short-doc-change
```

مثال:

```text
docs/update-github-operating-model
```

---

## 4. دورة تنفيذ العنصر

أي عنصر عمل يجب أن يمر بالحد الأدنى التالي:

1. اختيار العنصر من `GitHub Project`.
2. التأكد من وجوده كـ `Issue` أو عنصر تنفيذي واضح.
3. نقل العنصر إلى `Ready` ثم `In Progress`.
4. إنشاء فرع جديد من `dev`.
5. تنفيذ المطلوب داخل الفرع.
6. كتابة `Commit` واضح.
7. رفع الفرع إلى `GitHub`.
8. فتح `Pull Request` إلى `dev`.
9. تنفيذ المراجعة ومعالجة الملاحظات.
10. بعد الموافقة والدمج، ينقل العنصر إلى `Testing`.
11. بعد التحقق النهائي، ينقل إلى `Done`.

إذا طلبت تعديلات أثناء المراجعة، ينقل العنصر إلى `Changes Requested` حتى تستكمل.

---

## 5. حالات GitHub Project المرتبطة بالتدفق

الحالات الأساسية المعتمدة:

- `Backlog`
- `Ready`
- `In Progress`
- `Review`
- `Changes Requested`
- `Testing`
- `Done`

إذا تعثر العنصر، لا يستخدم `Blocked` كحالة مستقلة، بل:

- يبقى في حالته الحالية
- يوسم بـ `blocked`
- يوضح سبب التعثر في البطاقة أو التعليقات

---

## 6. قواعد إنشاء Branch

1. يجب أن يبدأ كل `feature` أو `bugfix` أو `docs` من `dev`.
2. يمنع إنشاء فرع عمل من `main`.
3. يمنع الدمج المباشر إلى `dev` أو `main`.
4. يجب أن يكون اسم الفرع واضحاً ومرتبطاً بالمهمة.
5. يمنع استخدام أسماء عامة مثل:

```text
test
update
new
final
my-work
```

---

## 7. قواعد Commit Messages

الصيغة الموصى بها:

```text
type: short description
```

الأنواع الأساسية:

```text
feat
fix
docs
refactor
test
chore
```

أمثلة:

```text
feat: add ai minutes draft workflow
fix: prevent invalid voting eligibility
docs: align github project operating model
test: add quorum validation tests
chore: initialize flutter web ci
```

---

## 8. قواعد Pull Request

لا يتم دمج أي عمل إلى `dev` أو `main` بدون `Pull Request`.

كل `Pull Request` يجب أن يحتوي على:

1. عنوان واضح
2. وصف مختصر لما تم تنفيذه
3. رابط أو رقم `Issue`
4. ما تم اختباره
5. لقطات شاشة عند تعديل الواجهات إذا لزم

ويجب كذلك:

- ربطه بعنصر في `GitHub Project`
- تعيين `Reviewers`
- توضيح أثره على الوثائق أو الحالات أو الصلاحيات إذا وجد

---

## 9. قواعد المراجعة والدمج

1. يجب مراجعة كل `Pull Request` قبل الدمج.
2. لا يدمج العمل إلى `dev` إلا بعد نجاح المراجعة.
3. إذا وجدت ملاحظات، يجب معالجتها قبل الدمج.
4. لا يرقى العمل إلى `main` إلا ضمن دفعة إصدار مستقرة.
5. يجب أن ينجح `CI` قبل السماح بالدمج.

---

## 10. قواعد ما قبل الدمج

قبل فتح `Pull Request` يجب التأكد من:

1. أن العمل يعمل محلياً دون أخطاء واضحة.
2. أن العنصر يحقق المطلوب.
3. عدم رفع أي أسرار أو مفاتيح.
4. عدم كسر مسار آخر في النظام.
5. تحديث التوثيق إذا استلزم التغيير ذلك.
6. التحقق من اتجاه النص العربي وسلامة الواجهة إذا كان التغيير في `Flutter`.
7. التحقق من الصلاحيات والعزل إذا كان التغيير في `Supabase` أو البيانات.

---

## 11. ملاحظات حاكمة

- `GitFlow` هنا خاص بإدارة الفروع والدمج فقط.
- إدارة التنفيذ اليومي تبقى عبر `GitHub Projects` وبمنهجية `Scrumban`.
- لا ينبغي إدخال تعقيد أعلى من حاجة الفريق الصغير.
- التوحيد مع المشاريع الأخرى يكون في الأساسيات، مع إبقاء خصوصية `Qarar` في المحتوى الوظيفي.
