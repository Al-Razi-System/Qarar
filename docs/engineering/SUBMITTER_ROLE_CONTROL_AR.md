# دور مقدم الموضوع — خريطة الأثر قبل التنفيذ

## القرار والثابت

دور المقدم صلاحية مستقلة مرتبطة بملف نطاق التقديم، لا عضوية مجلس وهمية.
تعيين نطاق محفوظ ينشئ هذا الدور؛ تعطيله يحفظ اختيارات المجالس ويوقف هذه
المنحة وحدها، دون سحب صلاحية تاريخية من دور آخر أو تعديل الموضوعات السابقة.
حالة الهوية وإلزام الكلمة المؤقتة والتصويت لا تتغير. لا نخمن دورًا عامًا
بصلاحية لكل المجالس. اختيارات أنواع المجالس والتفرعات تبقى كما هي.

## العقود والمستهلكون

- profiles/grants V2: إضافة submission_enabled الافتراضي true تحفظ السلوك
  السابق. الحساب بلا ملف لا يستحق دورًا. get_scope يعرض الحالة الجديدة.
- actor_can_submit_scoped_v2: يتطلب ملفًا مفعّلًا بالإضافة إلى القيود السابقة؛
  المستهلكون has_permission/actor_has_permission/get_topic_form_options،
  سياق التنقل، list_effective_topic_types/prepare/create_topic_from_type.
- عقد جديد set_user_submission_enabled_v2، مدير نظام في المؤسسة فقط؛ قفل
  المستخدم ثم ملف النطاق مثل الحفظ السابق. revision مشتركة تمنع تنازع
  حفظ النطاق والتعطيل؛ receipt مستقل يقيد التكرار بنفس المدخل، audit حقيقي.
  لا نغير توقيع save_scope ولا نعيد تفعيله ضمنيًا عند حفظ النطاق.
- API scope PATCH: جلسة/MFA/origin/body/UUID/revision، بلا service-role.
- UI scope: الدور وحالته وإجراء التعطيل/التفعيل مع بقاء المعاينة؛ إذا بقيت
  اختيارات غير محفوظة يمنع إجراء الحالة حتى الحفظ أو إعادة التحميل.
- لا jobs/إشعارات/كيانات جديدة أو تغيير في حالات الموضوعات والتصنيفات.
- قبل: ملف مفعّل ونطاق؛ بعد: ملف معطل ونفس النطاق، والعكس بعد تحقق وجود
  نطاق محفوظ. الفشل يتراجع ذريًا؛ نتائج غير مؤكدة تتطلب إعادة تحميل.

## الاختبارات والإصدار

اختبار فاشل أولًا: تعطيل يسحب منحة التقديم، ويحفظ القواعد؛ تعديل النطاق
المعطل لا يعيد التفعيل؛ إعادة التفعيل والتكرار والتعارض ومنع العادي/الأجنبي.
اختبار مجالس/تصنيفات مسموحة وممنوعة بفاعل مقدم غير مدير، ثم إنشاء موضوع
والتعطيل/إعادة التفعيل. نطاق وكلمة مؤقتة وأدوار متعددة مجاورون، desktop/mobile،
lint/typecheck/governance. التطوير المعزول فقط؛ الإصلاح الأمامي للترحيل.

## تنسيق فرع التصميم

المطور الآخر يوحد الألوان والخطوط والمكونات المشتركة؛ هذه الدفعة لا تعدل
CSS أو tokens أو الخطوط. الملفات الوظيفية المحتمل التقاء تغييراتها:
user-submission-scope.tsx وuser-roles.tsx. عند معرفة اسم فرعه نفحص فروق
الملفات ودمجًا تجريبيًا، ثم النوع/الوصول/RTL/الاستجابة والرحلات بعد الدمج.
غياب تعارض Git النصي وحده لا يكفي. لا دمج تلقائي ولا استبدال لتصميمه.

فحص origin/design/foundation-tokens الخاص بطلب #130: الملفات الجديدة/المعدلة
مستقلة عن تغييرات هذه الدفعة، وتجربة git merge-tree بين الالتزامين الحاليين
نجحت دون تعارض نصي. تعديلات العمل غير الملتزمة لا تمس ملفات طلب التصميم.
هذا ليس دمجًا ولا فحصًا بصريًا للخط الجديد. يجب اختبار الشاشات المذكورة في
طلبه بعد دمج مرحلي مأذون. عُيد إنتاج اختبار الشريط الجانبي الفاشل محليًا؛
تُصحح توقعات اسم الرابط إلى تصنيفات الموضوعات مع الحفاظ على فحص الوجهة
وعدم عرض الرابط لغير المخول؛ لا تغيير في صلاحيات التنقل أو الشاشة.
