# إنشاء مباشر بكلمة مرور مؤقتة — خريطة الأثر

## الثابت والرحلة قبل التنفيذ

مدير النظام فقط ينشئ حسابًا مباشرًا بكلمة مرور مؤقتة، دون دعوة أو بريد
مرسل. لا تُسجّل كلمة المرور في التدقيق أو الاستجابة ولا يُطلب UUID.
يظل خيار الدعوة متوافقًا. الحساب المباشر نشط للهوية لكنه محجوب عن بيانات
وعمليات المؤسسة حتى استبدال كلمة المرور. لا نخفي الحجب في الواجهة فقط.

الرحلة: مدير AAL2 ← إنشاء Auth غير مؤكد البريد ← finalization ذري لملف
المستخدم وعضويته الأولية وعلامة الإلزام وبصمة كلمة Auth الحالية ← تأكيد
البريد في Auth ← دخول بكلمة مؤقتة ← جلسة استبدال قصيرة دون جلسة تطبيق ←
استبدال الكلمة والتحقق أن بصمتها تغيرت ← إلغاء كل الجلسات المؤقتة وإزالة
الحجب ذريًا ← دخول جديد، ومعه MFA إن كان الدور يتطلبه.

## العقود والمستهلكون المثبتون

- `iam-admin/create_user`، `POST /api/admin/users` ونموذج الإنشاء؛ الوضع
  الجديد `temporary_password` وخيار الدعوة السابق. الإيصال يميز نجاحهما.
- `service_finalize_invited_user` يكوّن الملف والعضوية الحالية؛ عقد جديد
  يغلّفه ولا يغير توقيع عقد الدعوة. تُمَرَّر جلسة الفاعل الحية في تهيئة
  claims للخدمة حتى يظل الإنشاء ممكنًا للحسابات الجديدة بعد استبدال الكلمة.
  تحققنا من تعريفه ومن صلاحيات IAM executor
  على `auth.users` و`auth.sessions` في قاعدة التطوير.
- `qarar_iam.users`: حقول إلزام وبصمة داخلية وحجز محاولة واستحقاق جلسة حية؛
  الحقول القديمة وUUID والسجلات القديمة لا تتغير، والقيم الافتراضية لا
  تحجب أي حساب سابق. لا تُعرض البصمة في عقود الحساب.
- `current_organization_id` و`is_system_admin`: يرفضان الحساب المحجوب؛
  وبعد استبدال الكلمة يتطلب هذا الحساب جلسة Auth حية، كي لا يصبح JWT
  المؤقت القديم صالحًا بمجرد إزالة الحجب. حسابات الاختبارات/التكامل
  التاريخية التي لا تملك session_id تبقى كما هي.
- كشف فحص JWT الحقيقي أن `get_current_user_access_context` يبني سياقًا
  مباشرة من users دون شرط current_organization_id. يجب حجب هذا السياق
  أيضًا للهوية المؤقتة ولجلسة أُلغيت، بترحيل أمامي يحافظ على توقيعه
  واشتقاق roles/permissions/nطاق التقديم السابق. مستهلكوه الدخول وMFA
  وحواجز الصفحة وقراءة الحساب والشريط؛ السياق المرفوض يصبح null.
- دخول Next/نموذج الدخول، صفحة استبدال مستقلة عن layout الإدارة، كوكي
  `qarar_temporary_access_token` لمدة 15 دقيقة دون كوكي التطبيق/التحديث.
- API استبدال: يتحقق من هوية الكوكي عبر Auth، لا يقبل هدف العميل، يستخرج
  معرفه فقط، ويحجز محاولة قبل تحديث Auth. لا تزامن لتحديثين لنفس المستخدم.
  يتحقق أيضًا من الكلمة الحالية عبر Auth ويرفض تطابقها مع الجديدة؛ تغيير
  بصمة bcrypt وحده لا يثبت اختلاف النص عند إعادة التشفير.
- وظائف الخدمة الجديدة مقيدة بـservice_role، مسجلة في architecture،
  مع تدقيق إنشاء/استبدال واضح بالفاعل الحقيقي.
- trigger `audit_users_changes` يستخدم `audit_row_change` ويحفظ صف المستخدم
  كاملًا. يجب إسقاط بصمة الكلمة وحقول حجز الاستبدال من old/new لجدول
  users فقط، مع إبقاء قواعد user_invitations وسائر الجداول كما هي.
  ترحيل تصحيحي أمامي مستقل، واختبار عدم وجود هذه المفاتيح في التدقيق
  قبل تغييره. لا نمحو سجل التدقيق السابق أو نعيد كتابة التاريخ.
- API الإنشاء يثبت action بعد مدخلات العميل، فلا يسمح بتبديل العملية.
- بحث المستهلكين أثبت أن `qararEdge` يستخدمه إنشاء المستخدم وعمليات
  المستخدم والجلسات فقط. فقدان HTTP status في الخطأ يحول فشل الإنشاء
  غير المؤكد إلى 400 قابل للتكرار. نحفظ status في Error نفسه (دون تغيير
  صنفه كي تبقى خريطة أخطاء الجلسات متوافقة)، وtraceId من Edge إلى API
  الإنشاء وسجل الخادم. لا تتغير صلاحيات أو payload أي عملية.
- كشف اختبار المتصفح أن زر فتح الإنشاء قد يستقبل النقر قبل اكتمال
  hydration دون فتح النافذة. يجب أن يبقى معطلًا حتى تصبح الواجهة جاهزة؛
  اختبار HTML الخادم أولًا ثم فتح النافذة في الاختبار التفاعلي.

## الفشل والتوافق والإصدار

فشل إعداد DB يمنع تأكيد Auth الجديد؛ محاولة تعويض Auth تخص الهوية الجديدة
فقط. إن فشل التعويض يبقى الحساب غير مؤكد/محجوب، وتظهر نتيجة إنشاء غير
مؤكدة لا يُعاد معها الإنشاء عمياء. فشل تحديث كلمة Auth يبقي الحجب. فشل
إكمال DB بعد تحديثها يبقي الحجب أيضًا؛ يُرشد المستخدم لتسجيل الدخول
بالجديدة ثم الاستكمال. الحجز ينتهي بعد خمس دقائق، ويمكن تحريره بنفس
معرف المحاولة فقط. لا تُمسح كلمات مرور الحسابات السابقة.

ترحيل أمامي جديد فقط وعلى التطوير المعزول أولًا. لا تغيير في membership
ولا دور مقدم موضوع ولا الصورة ضمن هذه الدفعة. بوابات الإنتاج السابقة
والانحراف لا تُلغى.

## خطة الاختبارات

اختبار Edge قبل الكود للوضع الجديد/رفض غير المدير/كلمة ضعيفة/دون بريد؛
pgTAP للحجب في DB والوظائف الخاصة والحجز المتزامن وبصمة لم تتغير وإلغاء
جلسات مؤقتة قديمة ونجاح جلسة جديدة وتدقيق الفاعل؛ عقود Next/UI للدخول
والإنشاء والرد غير المؤكد؛ متصفح على dev بحسابات معزولة: إنشاء ثم محاولة
وصول قبل الاستبدال ثم استبدال ودخول جديد ورفض القديمة، desktop/mobile.
تحقق من مسار الدعوة السابق و06/44/83/13، ثم lint/typecheck وحوكمة التطوير.

## نتائج التحقق وبوابات الإصدار

- فشل اختبار الوضع المباشر أولًا، ثم نجحت 22 حالة Edge تشمل الدعوة
  السابقة ورفض غير المدير وسياسة كلمة المرور.
- نجحت 69 حالة واجهة وعقد في 15 ملفًا تشمل الحساب الشخصي والنطاق والدخول
  والإنشاء والاستبدال والخروج. نجح اختبارا جاهزية النافذة مرة أخرى بعد
  تصحيح نوع محدد الاختبار، دون تعديل سلوك المستخدم.
- نجحت 95 حالة pgTAP في الملفات 84 و06 و44 و83 و13، بينها صلاحيات
  مسموحة ومرفوضة، والتزامن وإبطال JWT القديم وحجب السياق وتنقيح التدقيق.
- typecheck ناجح؛ lint دون أخطاء مع ستة تحذيرات سابقة غير مرتبطة؛
  `test:development-governance` ناجح و147 وثيقة UTF-8 سليمة.
- اختبار المتصفح السابق كشف عيب حجب سياق المؤسسة وعولج بترحيل 220
  واختبار انحدار. نجحت الرحلة النهائية `test-temporary-password-dev-browser.mjs`
  على dev: إنشاء من واجهة المدير دون دعوة، كوكي استبدال فقط، رفض وصول
  الحساب المؤقت، رفض كلمة حالية خاطئة، تغيير فعلي، إلغاء الجلسات وحجب JWT
  القديم، دخول جديد بالكلمة الشخصية، رفض المؤقتة القديمة، وتدقيق الفاعل.
  نجح العرض بعرضي 1440 و390 دون تجاوز أفقي وشوهدت الصور. عُطّلت هويات
  الاختبار المعزولة في Auth بعد التشغيل وحُفظ التاريخ؛ لم تُمس بيانات فعلية.
- فحص سجل الترحيلات على التطوير يرصد 17 اسمًا سابقًا مسجلًا بتاريخ فقط،
  مقابل أسماء المصدر الكاملة؛ الترحيلات الثلاث الجديدة لها أسماء وبصمات
  مطابقة. لا نعيد كتابة السجل السابق ضمن إصلاح الحساب.
- فحص توثيق العقود على التطوير يطابق مرجع 227 عقدًا، لكنه يفشل في توثيق
  تشغيل/استجابة 14 عقدًا سابقًا للمسارات السابقة ودورية الاجتماعات. عقود
  الخدمة الخمسة الجديدة موثقة. لا نشر إنتاجي مع هاتين البوابتين الفاشلتين.
