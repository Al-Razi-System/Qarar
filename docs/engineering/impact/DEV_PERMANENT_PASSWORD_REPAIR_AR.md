# خريطة أثر تحويل كلمات مرور مستخدمي التطوير إلى دائمة

التاريخ: 21 أكتوبر 2026
النطاق: قاعدة `devqarar` المحلية، مؤسسة العرض `00000000-0000-0000-0000-000000000001` فقط

## الرحلة والثابت التجاري

- **المشكلة:** انتهت مدة كلمات المرور الأولية لحسابات العرض، فأصبح المستخدم يرى رسالة انتهاء الصلاحية ولا يستطيع الدخول.
- **المطلوب:** الإبقاء على كلمة المرور الحالية لكل حساب كما هي، وإلغاء بوابة «كلمة مرور مؤقتة» عنها لتصبح كلمة دائمة.
- **الثابت:** لا تُقرأ كلمات المرور الصريحة ولا يعاد تعيين تجزئات `auth.users.encrypted_password`. لا يشمل الإصلاح الإنتاج أو مؤسسات اختبارات pgTAP.
- **السابق:** مستخدم نشط، لكن `must_change_password=true` ومرور سبعة أيام يمنعان إكمال الدخول.
- **الانتقال:** إصلاح تطويري إداري، ذري ومدقق، يلغي الجلسات القديمة ثم يمسح خط أساس الكلمة المؤقتة وحقول مطالبة التغيير.
- **اللاحق:** مستخدم نشط بكلمة المرور الحالية نفسها، `must_change_password=false`، ويلزم أن ينشئ تسجيل الدخول التالي جلسة مصادقة حية جديدة.
- **الفشل/الرجوع:** أي حساب مفقود من Auth، غير نشط، بلا كلمة مرور، أو لا تطابق تجزئته خط الأساس يوقف المعاملة كاملة قبل أي تعديل. الرجوع -إن لزم- يكون بإعادة إصدار كلمة أولية جديدة من عقد الإدارة، لا باستعادة التجزئة المؤقتة القديمة.

## المستهلكون والعقود والبيانات

- تتأثر شاشة `/login`، ودالة `service_get_temporary_password_state`، وبوابة `current_organization_id` فقط من خلال حالة المستخدم المخزنة.
- لا يتغير API أو RPC أو مخطط قاعدة البيانات أو منطق إنشاء المستخدمين الجدد؛ تبقى كلماتهم الأولية مؤقتة وفق السياسة الحالية.
- الأعمدة المصححة: `must_change_password` و`require_live_auth_session` و`temporary_password_hash` وحقول المطالبة/الإيصال.
- تُلغى صفوف `auth.sessions` الحالية للأهداف، وتوسم جلسات قرار المناظرة بأنها ملغاة، لمنع ترقية جلسة مؤقتة قديمة بعد إزالة البوابة.
- يضاف سجل تدقيق لكل حساب بالفعل `iam.temporary_password.permanentized_by_dev_repair`، مع مصدر الإصلاح ومن دون كلمة أو تجزئة أو مطالبة سرية.

## الصلاحيات والسجلات القديمة

- المنفذ هو مسؤول النظام التجريبي الثابت، ويُتحقق من نشاطه وصلاحية مسؤول النظام داخل المؤسسة قبل التعديل.
- النطاق يلتقط فقط الحسابات الحالية ذات `must_change_password=true` في مؤسسة العرض. سجلات مؤسسات الاختبارات مستثناة عمدًا.
- الإصلاح idempotent: الإعادة لا تجد أهدافًا ولا تكرر سجلات التدقيق.
- الملف منفصل عن بيانات البذر ولا يُشغّل تلقائيًا في الترحيلات أو الإنتاج.

## التحقق

1. قبل التعديل: عدّ الأهداف، والتأكد أن جميعها نشطة ولها سجل Auth وكلمة حالية تطابق خط الأساس المؤقت.
2. أثناء المعاملة: قفل الأهداف، سحب الجلسات، تحديث الحالة، وإضافة التدقيق.
3. بعد التعديل: صفر حسابات مؤقتة في مؤسسة العرض، صفر حقول مؤقتة متبقية، وبقاء جميع الحسابات النشطة وكلمات Auth دون تعديل.
4. فحص الحساب الظاهر في البلاغ والتأكد أن حالته أصبحت دائمة وأن جلساته القديمة ألغيت.
5. تشغيل `npm run test:development-governance` لأن الملف إصلاح مستودعي موثق، مع عدم تعديل سلوك الإنتاج.
