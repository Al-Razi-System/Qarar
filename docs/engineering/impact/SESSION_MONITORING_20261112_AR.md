# خريطة أثر: مراقبة الجلسات وتسجيل جلسة المتصفح (12 نوفمبر 2026)

## العطل المرصود

صفحة «مراقبة الجلسات» (`/admin/sessions`) فارغة دائمًا، و`qarar_iam.user_sessions` على
`devqarar` فيه 0 صفوف رغم وجود 200 جلسة حية في `auth.sessions`.

## السبب الجذري

1. العقد `register_user_session` موجود منذ يوليو، لكن لا شيء في لوحة التحكم يستدعيه عند
   إتمام الدخول (كلمة المرور أو التحقق الثنائي)، فلا يُسجَّل أي صف.
2. القائمة الجانبية تسمي الصفحة «مراقبة الجلسات» وتشترط `iam.sessions.manage`، لكن الصفحة
   تقرأ `list_my_sessions` فقط (جلسات المستخدم نفسه)، ولا يوجد عقد يعرض جلسات المؤسسة.
3. حالة الجلسة كانت تُستنتج من `revoked_at` وحده؛ الخروج العادي أو انتهاء الجلسة يحذف صف
   `auth.sessions` ولا يمس `user_sessions`، فكانت ستبقى «نشطة» للأبد.

## رحلة المستخدم والثوابت

- كل دخول ناجح إلى اللوحة يسجّل جهاز المتصفح (معرف جهاز ثابت في كوكي `qarar_device_id`)
  ويربطه بجلسة Auth الحالية من مطالبة `session_id` في JWT.
- «جلساتي» للجميع: جلسات المستخدم مع الحالة والجلسة الحالية.
- «جلسات المؤسسة» لحامل `iam.sessions.manage` أو `iam.users.manage` (القاعدة نفسها التي
  يطبقها `request_session_revocation`)، ضمن مؤسسته فقط.
- الحالة: `revoked` إن أُبطلت، `active` إن بقيت جلسة Auth قائمة وغير منتهية، وإلا `ended`.
- الإبطال يبقى عبر `iam-admin/revoke_session` دون تغيير؛ قاعدة «لا يبطل جلسات مسؤول النظام
  إلا مسؤول نظام» قائمة في `service_revoke_auth_sessions`.

## المستهلكون والعقود

- جديد: `api_v1.admin_list_sessions(p_status, p_query, p_limit, p_offset)`.
- معدّل بإضافة حقول فقط: `qarar_iam.list_my_sessions()` تضيف `status`, `is_current`,
  `last_activity_at`. الحقول القديمة باقية بأسمائها وقيمها، فأي مستهلك آخر للعقد لا يتأثر بالإضافة.
- `register_user_session` بلا تغيير؛ تستدعيه الآن `/api/auth/login` و`/api/auth/mfa`.
- مسار `/api/admin/sessions` يقبل `?scope=organization&status=`.

## البيانات القائمة والترحيل

- ترحيل أمامي `20261112050000_session_monitoring.sql`.
- إصلاح بيانات لمرة واحدة، idempotent ومحدد: ينسخ جلسات `auth.sessions` الحية إلى
  `user_sessions` بمعرف جهاز `auth-session:<id>` و`on conflict do nothing`، كي تظهر
  الجلسات الجارية الآن. كل صف يمر بمشغّل التدقيق القائم. لا يمس أي جلسة منتهية.

## الفشل

- فشل التسجيل لا يمنع الدخول: يُسجّل `session.register_failed` بسبب داخلي قابل للتتبع، ويستمر
  المستخدم. السبب: المراقبة ميزة متابعة، والإبطال الفعلي يعمل على `auth.sessions` مباشرة.
- رفض عقد المؤسسة لغير المخول برسالة عربية آمنة؛ الواجهة لا تعرض التبويب له أصلًا.

## الاختبارات

- قاعدة البيانات `154_session_monitoring_test.sql`: الحالة الثلاثية، العزل بين المؤسسات،
  رفض غير المخول، والجلسة الحالية.
- مسار الدخول: يستدعي التسجيل بمعرف الجهاز ومعرف جلسة Auth، ولا يفشل الدخول إن فشل.
- واجهة الجلسات: تبويب المؤسسة يظهر للمخول فقط ويعرض المستخدم والحالة.
