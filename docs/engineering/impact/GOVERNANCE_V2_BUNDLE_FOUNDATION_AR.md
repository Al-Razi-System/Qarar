# خريطة أثر تأسيس حزمة الحوكمة V2

## تعريف التغيير

- الحاجة: لا يجوز تنفيذ أوامر API V2 قبل وجود جذر تجميعي يضبط المسودة والمراجعة والاعتماد والتفعيل.
- الثابت التجاري: تحفظ إعدادات نوع الموضوع كوحدة واحدة، ولا يعتمد المُعد عمله بنفسه، ولا تصبح أي حزمة فعالة بهذا الترحيل.
- السلوك الحالي: جداول V2 إعدادات معزولة بلا حزمة أو API أو بيانات إنتاجية.
- السلوك المتوقع: حزمة معزولة تربط إصدار نوع واحد، وتسجل حالتها ومراجعاتها وإيصالات الأوامر المستقبلية.
- خارج النطاق: واجهة المستخدم واستيراد ملف Excel وتعديل بيانات V1. أضيفت أوامر RPC داخلية تدريجياً للحفظ والإرسال والمراجعة والتفعيل، ولا تُعرض بعد عبر API العام.

## خريطة الرحلة

- السابقة: إنشاء إعدادات V2 غير مفعلة.
- المعدلة: تجميع الإعدادات في حزمة مسودة ذات رقم مرجعي ونسخة تعارض.
- التالية: التحقق ثم الإرسال ثم الاعتماد المستقل ثم التفعيل. لا يبدأ استهلاك V2 من رحلات الموضوعات إلا بعد بوابة قطع مستقلة.
- الحالة قبل العملية: لا توجد حزمة.
- شروط السماح المستقبلية: مؤسسة ومستخدم حاليان، صلاحية سياقية، `client_request_id`، وإصدار متوقع.
- الحالة بعد النجاح: حزمة `draft` غير فعالة.
- الفشل: لا كتابة جزئية، ولا إيصال نجاح، ورسالة عربية آمنة من طبقة الأمر المستقبلية.

## خريطة التأثير

- الواجهات: لا تغيير حالياً.
- API/RPC: أوامر داخلية فقط لمنفذ الحوكمة؛ لا تعريض عام ولا ربط بواجهة المنتج.
- البيانات: ثلاثة جداول إضافية فقط داخل `qarar_governance`.
- الحالات: `draft → under_review → changes_requested/approved → effective → retired`.
- الأدوار: لا منح مباشر لـ`anon` أو `authenticated` أو `service_role`؛ منفذ وحدة الحوكمة فقط.
- القديم والجاري: لا قراءة ولا تحديث لجداول V1 أو السجلات الجارية.

## خطة الاختبار والإصدار

- اختبار بنيوي يفشل قبل الترحيل ويثبت الجداول والقيود والعزل ومنع التفعيل الضمني.
- اختبار قاعدة بيانات للملكية وRLS والمنح والفصل بين المُعد والمراجع وإعادة الطلب.
- تطبيق محلي فقط ثم بوابات العقود وقاعدة البيانات؛ لا إنتاج ولا ترحيل بيانات. تفعيل الحزمة لا يفعّل استهلاك V2 في الموضوعات ولا يلمس V1.
- الرجوع يكون بإصلاح أمامي قبل أي استعمال، ولا يعدل هذا الترحيل بعد مشاركته.
