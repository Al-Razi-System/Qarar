# سلامة نموذج الدخول قبل تفعيل الواجهة

- العطل: نموذج الدخول بلا method ينفذ GET قبل ربط أحداث React، فيضع بيانات الاعتماد في الرابط.
- الثابت: لا ترسل بيانات الاعتماد عبر URL، ولا يسمح بالنقر قبل جاهزية الواجهة.
- الرحلة: صفحة الدخول ← POST JSON إلى عقد الدخول الحالي ← MFA أو لوحة الإدارة. الفشل يبقي المدخلات ورسالة الخطأ في النموذج.
- التأثير: LoginForm فقط؛ عقد الدخول وملفات تعريف الارتباط وقرارات MFA والأدوار وقاعدة البيانات دون تغيير.
- الحل: POST دفاعي وتعطيل حقول النموذج حتى hydration مع رسالة جاهزية واضحة، ومنع الطلب المتكرر أثناء التنفيذ.
- الاختبار: HTML الخادم يحتوي method POST وfieldset معطلاً؛ الواجهة المفعلة ترسل JSON وتنتقل إلى MFA، وفشل الشبكة ظاهر بجوار العملية.
- الإصدار: Hot Reload في نطاق التطوير، تحقق متصفح قبل الاعتماد؛ لا ترحيل بيانات.
- الاعتماد التشغيلي: السماح صراحة بنطاق التطوير عبر QARAR_ALLOWED_DEV_ORIGINS؛ سجل Next أظهر طلب ضبط allowedDevOrigins للنطاق. التأثير محصور بخدمة dashboard-dev وموارد JavaScript/HMR؛ لا تعديل لحماية الإنتاج. إعادة إنشاء خدمة التطوير فقط لتطبيق متغير البيئة.

## متابعة اختلاف نسخ HTML وJavaScript

- الدليل: خطأ المستخدم يعرض LoginForm القديم في العميل (mt-8 space-y-5 دون fieldset) مقابل HTML الجديد. استجابة ملف التطوير من الأصل Cache-Control: no-cache, must-revalidate بينما استجابة Cloudflare max-age=14400, must-revalidate.
- الثابت: لا تخزن أصول خادم التطوير المتغيرة في المتصفح أو الوسيط؛ الإنتاج يحتفظ بسياسة أصوله غير المتغيرة.
- التأثير: إعداد headers في Next الخاص بالتطوير فقط، جميع صفحات وأصول التطوير؛ لا تغيير لعقود auth/MFA أو البيانات أو الأدوار. السجلات الجارية تبقى سليمة. الفشل يبقي الخدمة السابقة؛ الرجوع إزالة ترويسة التطوير.
- الاختبار: اختبار إعداد no-store في التطوير وعدم فرضه على الإنتاج؛ فحص ترويسة الملف من الأصل والدومين، ودخول ثم MFA في متصفح بعرضين وإعادة تحميل الصفحة دون أخطاء hydration. النسخ المخزنة قبل الإصلاح تحتاج تحديثًا قسريًا مرة واحدة.
- نتيجة المتابعة: اختبار الإعداد فشل أولاً في development ثم نجحت الاختبارات الأربعة عشر بعد التصحيح. الأصل والدومين يعيدان no-store, max-age=0 وحالة Cloudflare BYPASS. متصفح Chromium بعرضي 1440 و390 مع إعادة تحميل عادية ثم الدخول إلى MFA: لا pageerror ولا أصول قابلة للتخزين ولا تجاوز أفقي. نجحت TypeScript وESLint وفحوص development-governance. لا تغيير Nginx أو الإنتاج لهذه المتابعة.
- إعادة تحقق قابلة للتكرار: افتح /login، أعد التحميل عاديًا، افحص أن استجابات /_next/static تحمل no-store، ثم أدخل حساب التطوير وتأكد من الوصول إلى MFA دون hydration error؛ كرر بشاشة ضيقة. HTTP 200 وحده ليس معيار النجاح.

## تحرير حظر اختبار حساب التطوير

- أثبت Redis في خدمة التطوير أن عداد بريد مدير النظام وصل إلى 6 مع TTL متبقٍ 262 ثانية؛ الإعداد الحالي 5 محاولات خلال 900 ثانية، ويحتسب محاولات الدخول الناجحة أيضًا. الاختبارات المتكررة استهلكت الحد.
- الإجراء التشغيلي المحدد: حذف مفتاح عداد البريد لهذا الحساب فقط في Redis التطوير، بعد قراءة قيمته. لا حذف شامل ولا تعديل لحماية الإنتاج أو عدادات IP/global أو حسابات Auth أو الأدوار. لا تغيير سلوكي أو ترحيل بيانات.
- التحقق: المفتاح المحدد يعود غير موجود، وتبقى سياسة تحديد المحاولات فعالة. تجنب إعادة اختبارات الدخول المتكررة على الحساب نفسه أثناء قبول المستخدم؛ نجاح التصفير وحده لا يثبت نجاح الدخول التالي للمستخدم.

- قبل الإصلاح فشل اختبار HTML الخادم لأن method POST لم يكن موجودًا.
- بعد الإصلاح: 12 اختبارًا ناجحًا للنموذج وعقد الدخول، وفحص TypeScript وESLint للملفات المعدلة ناجحان، وفحص development-governance ناجح.
- متصفح Chromium على نطاق التطوير: دون JavaScript النموذج POST وزر الإرسال معطل؛ مع JavaScript نجح الدخول وانتقل إلى MFA.
- بعرض 390px ظهر زر إعداد تطبيق المصادقة بعد تحميل السياسة، دون تجاوز أفقي أو خطأ JavaScript. لم يتم إنشاء عامل MFA أو تعديل الحساب أثناء التحقق.
- تم تحديث خدمة التطوير وإعادة تحميل إعداد Nginx الحالي لتجديد عنوان الحاوية بعد إعادة إنشائها؛ لم تتغير قاعدة بيانات الإنتاج أو بيانات المستخدمين.
