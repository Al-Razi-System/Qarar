# استكمال دليل الصلاحيات النظامية

## خريطة الأثر قبل التنفيذ

- الحاجة: مؤسسة التطوير تحتوي 21 تعريفًا فقط؛ صلاحيات تشغيل النظام موجودة
  في العقود لكن أغلب تعريفاتها كانت تزرع للمؤسسات الموجودة وقت الترحيل فقط.
- القاعدة: تسجيل قدرة النظام لا يمنحها لدور أو مستخدم. يختار الإداري الصلاحيات
  من الدليل العربي وتبقى رحلة الطلب والاعتماد والسياق كما هي.
- السابقة: ترحيل/إنشاء مؤسسة. المعدلة: تهيئة تعريفات الصلاحيات الناقصة.
  التالية: admin_list_permissions ثم اختيارها وطلب تغيير الدور واعتماده.
- الحالة: تعريف مفقود → تعريف نظامي نشط غير ممنوح. التعريف الموجود، بما فيه
  المعطل أو ذو اسم مخصص، يبقى بمعرفه ونطاقه وحالته. الفشل يتراجع ذريًا.
- العقود: لا API جديد ولا تغيير لواجهة RPC القائمة. دوال صيانة داخلية فقط،
  لا ينفذها authenticated أو anon أو service_role. تسجيلها في سجل المعمارية.
- الجداول: qarar_iam.permissions فقط، وسجل التدقيق؛ لا تعديل role_permissions
  أو memberships أو المستخدمين أو نطاقات التقديم أو كلمات المرور أو طلبات الاعتماد.
- المصدر: رموز ونطاقات العقود الحالية وترحيلات التسجيل الأصلية؛ تمت مقارنة
  تعريفات الإنتاج للقراءة فقط. لا نسخ منح الأدوار من الإنتاج، ولا اختراع أذونات
  للمحاضر أو التنفيذ اللذين يستخدمان سلطات سياقية ومكلفين داخل عقودهما.
- تعريفات التوافق التاريخية محفوظة؛ لا تتحول أحداث التدقيق إلى صلاحيات.
  اختيار صلاحية لا يلغي اشتراط الرئيس/المقرر/الحاضر أو حالة العملية.
- المشغل: مؤسسات جديدة تتلقى الدليل كاملًا؛ إصلاح المؤسسات السابقة يضيف
  المفقود فقط، قابل لإعادة التنفيذ ومراقب بتدقيق يتضمن الرموز المضافة.
- لا مهام مجدولة ولا إشعارات. لا ترحيل إنتاج أو دمج فروع في هذه المهمة.

## الاختبارات والإصدار

- اختبار DB فاشل أولًا يثبت نقص الدليل، ثم اختبار تهيئة مؤسسة جديدة،
  اكتمال جميع رموز بوابات الصلاحيات الحالية، وعدم منح الأدوار تلقائيًا.
- تكرار التهيئة لا يغير المعرفات أو الحالات أو الأسماء ولا يكرر التدقيق.
- رفض تنفيذ الصيانة من المستخدم/الخدمة، وعزل المؤسسات، والسماح بصلاحية
  المجلس المعين ورفض مجلس آخر والنطاق العام والإدارة دون منحة.
- رحلة متصفح وHTTP معزولة للدليل واختيار الصلاحية والطلب والاعتماد.
- ترحيل أمامي جديد؛ يطبق أولًا داخل معاملة تُلغى للاختبار، ثم على التطوير
  مع checksum في سجل الترحيلات. لا منح تلقائي ولا إعادة تنشيط تعريفات معطلة.
- الرجوع عند الحاجة بتصحيح أمامي لدليل التعريفات، لا حذف تعريف صار مرتبطًا
  بطلب أو دور. اختبارات العقود وحوكمة التطوير مطلوبة قبل التسليم.

## نتائج التطوير

- أُعيد إنتاج النقص باختبار فاشل: مؤسسة جديدة كانت تحصل على 21 تعريفًا.
  أصبحت تحصل على 61؛ تمت مطابقة جميع بوابات الصلاحيات النصية المثبتة.
- نجح اختبار DB92 (16 تحققًا)، واختبار منع الوصول الداخلي DB36 (5 تحققات).
- جُرّب الترحيل داخل معاملة أُلغيت أولًا، ثم طبق على التطوير فقط. لقطة كاملة
  لتعريفات الصلاحيات السابقة ولصفوف role_permissions أثبتت عدم تغيير أي منها.
- qarar-demo تلقى 40 تعريفًا مفقودًا، مع حدث تدقيق واحد بالرموز المضافة.
- سجل الترحيلات مطابق لـ281 ملف مصدر مع checksum. عقود API الموثقة مطابقة
  لـ227 عقدًا؛ لا RPC عام جديد ولا تغييرات على منح الإنتاج.
- نجحت رحلة المتصفح/HTTP بحسابات معزولة، دون زرع تعريفات اختبار: التهيئة،
  الاختيار والطلب، عدم منح مبكر، رفض الاعتماد الذاتي، اعتماد مسؤول ثانٍ، رفض
  المستخدم غير المخول، نطاق العضوية، التعطيل وإعادة التفعيل، 1440/390 والوضعان.
