# خريطة أثر إصلاح بوابة الاختبارات والعقود النهائية

## رحلة المستخدم والثابت التجاري

- يجب أن تُحمّل تفاصيل الموضوع ونسخه المصححة دون خطأ داخلي، مع بقاء عزل المؤسسة والصلاحيات السياقية كما هو.
- لا يجوز استدعاء دوال الوحدات الداخلية مباشرة من أدوار المتصفح أو من منفّذ وحدة أخرى؛ سطح الاستدعاء العام هو أغلفة `api_v1` و`api_v2` المسجلة فقط.
- يجب أن يتضمن دليل الصلاحيات النظامي `corrections.read` لكل مؤسسة حالية أو جديدة.
- لا تغيّر هذه الدفعة أي حالة موضوع أو اجتماع أو طلب تصحيح، ولا تضيف انتقالاً جديداً.

## المتصلون والمستهلكون والعقود

- أغلفة تفاصيل الموضوع وسجل اجتماعاته في `api_v1`، وشاشات تفاصيل الموضوع والاجتماع التي تستهلكها.
- أغلفة التصحيح الرسمي، وتقويم الاجتماعات وخطط المجالس، ومنفذ `qarar_api_executor`.
- `qarar_iam.system_permission_catalog()` ومزامنة دليل الصلاحيات للمؤسسات.
- سجلات `function_registry` و`api_contract_registry` واختبارات pgTAP الأمنية والتعاقدية.

## الحالة والانتقال والفشل

- قبل الإجراء وبعده: لا تغيير في حالات المجال أو الانتقالات المسموحة.
- الفشل الحالي: تركيب `SELECT INTO` غير صالح يمنع قراءة تفاصيل موضوع مصحح، وصلاحية `PUBLIC EXECUTE` الافتراضية تسمح بتجاوز أغلفة API.
- الفشل بعد الإصلاح: يُرفض الاستدعاء المباشر بصلاحية قاعدة البيانات، وتبقى أخطاء الواجهة العربية الآمنة صادرة من غلاف API.
- التراجع: لا تعديل رجعي لترحيل منفذ؛ الإصلاح بترحيل أمامي واحد، ويمكن عكس منح الصلاحيات أو تعريف الدالة بترحيل أمامي لاحق فقط.

## البيانات والترحيل

- لا تتغير بنية الجداول ولا السجلات التشغيلية.
- تُزامن `corrections.read` بطريقة idempotent لكل مؤسسة حالية، وتُنشأ تلقائياً للمؤسسات الجديدة من الدليل النظامي.
- لا seed ولا إصلاح سجل تجريبي، ولا حذف بيانات.

## الاختبارات الحامية

- الاختبارات الأمنية الفاشلة حالياً `14` و`36` تعيد إنتاج تسريب التنفيذ المباشر.
- اختبارات `10` و`16` تعيد إنتاج خطأ تفاصيل الموضوع وعزل المؤسسة.
- اختبار `92` يحمي اكتمال دليل الصلاحيات للمؤسسة الحالية والجديدة.
- تُحدّث الاختبارات القديمة التي تفترض عدداً سابقاً لعقود API أو اجتماعاً واحداً فقط من خطة مفتوحة، دون إضعاف الثوابت.
- تُختبر الدفعة أولاً على قاعدة E2E المعزولة، ثم على قاعدة التطوير بعد نسخة احتياطية، ولا تمس الإنتاج.
- يستخدم خادم Playwright مجلد بناء Next مستقلاً داخل مشروع الواجهة، حتى لا يفسد
  manifest خادم `devqarar` الجاري؛ لا يتغير مجلد `.next` الافتراضي إلا عند تمرير
  متغير E2E الصريح.

## أثر قناة الاجتماع بين عمليات الخادم

- رحلة المستخدم: عندما يغيّر الرئيس حالة بند أو تصويتاً، ترى شاشات أعضاء الاجتماع
  نفسه التغيير فوراً، ولا تتلقى اجتماعات أخرى أي إشارة.
- السبب الجذري: الناقل داخل ذاكرة عملية Next يعمل في التطوير أحادي العملية، لكنه لا
  يعبر عزل معالجات Route Handlers في بناء الإنتاج؛ لذلك بقيت الشاشة الأخرى حتى قراءة
  الاحتياط الدورية.
- العقود والمستهلكون: `POST /api/admin/meetings` ناشر فقط بعد نجاح العقد والتحقق من
  سياق الاجتماع، و`GET .../voting/live` مشترك؛ الإشارة لا تحمل صوتاً أو ملاحظة أو
  بيانات مستخدم، بل نوع التغيير ومعرّف الاجتماع والمراجعة فقط.
- الفشل والتراجع: تعطل Redis لا يفشل الإجراء التجاري الناجح؛ يبقى الناقل المحلي
  والقراءة الدورية الآمنة. لا تتغير حالات المجال أو صلاحياته، وكل شاشة تعيد القراءة
  بجلستها وصلاحيتها هي.
- حد الحمل: Redis هو المسار الفوري، أما لقطة قاعدة البيانات الدورية فشبكة تعافٍ كل
  عشر ثوانٍ. تشغيل ثلاث RPCs كل ثانية لكل شاشة تسبب فعلياً في استنزاف مهلات
  PostgREST وتعليق تحميل أعضاء آخرين، لذلك لا يجوز إعادته دون اختبار حمل صريح.
- البيانات: لا جدول ولا ترحيل ولا سجل أعمال جديد. مفاتيح Redis قصيرة العمر ومعزولة
  باسم الاجتماع، وتستخدم إعداد Redis المشترك الإلزامي نفسه دون كشف سر للمتصفح.
- الاختبار الحامي: سيناريو الاجتماع متعدد الحسابات يشترط ظهور بدء المناقشة وفتح
  التصويت خلال ثلاث ثوانٍ على سطح المكتب والجوال، مع اختبارات وحدة للعزل والتوقف
  والتراجع عند غياب Redis. نجحت الرحلة الكاملة على Chromium المكتبي والجوال،
  ونجحت اختبارات البث والعقود المركزة 25/25 على بناء production standalone.
