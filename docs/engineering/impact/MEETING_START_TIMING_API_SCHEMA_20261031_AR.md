# خريطة أثر: توجيه عقد توقيت بدء الجلسة إلى واجهته الصحيحة

## الرحلة والثابت التشغيلي

- بعد اعتماد جدول الأعمال يصبح الاجتماع `ready_to_start`، ويضغط الرئيس «فتح الجلسة».
- يجب قراءة توقيت البدء من الخادم قبل الفتح لتحديد إن كان الاجتماع داخل الموعد أو يحتاج تأكيداً صريحاً.
- فشل قراءة التوقيت يجب ألا يفتح الجلسة أو يغير حالتها.

## السبب والعقود والمستهلكون

- العقد `get_meeting_session_start_timing_v2` اسمه ينتهي بـ`_v2` لكنه منشور، حسب ترحيله ومرجع العقود، في مخطط `api_v1`.
- مسار `/api/admin/meetings` كان يختار المخطط من لاحقة الاسم فقط، فوجه العقد إلى `api_v2` وأعاد PostgREST الخطأ `PGRST202`.
- المستهلكان هما `MeetingDetailsJourney` و`MeetingsWorkspace` قبل استدعاء `open_meeting_session`.
- لا تتغير معاملات العقد أو استجابته أو صلاحياته.

## الحالة والانتقال والفشل

- قبل القراءة: `ready_to_start`.
- القراءة لا تغيّر الحالة.
- بعد قراءة داخل الموعد يمكن استدعاء الفتح؛ وخارج الموعد تظهر نافذة التأكيد.
- عند فشل القراءة يبقى الاجتماع `ready_to_start` وتظهر رسالة آمنة عند الإجراء.

## البيانات والترحيلات

- لا تغيير في قاعدة البيانات ولا ترحيل؛ الدالة موجودة فعلياً في `api_v1` وسجل الترحيل صحيح.
- الإصلاح في موزع API فقط، مع قائمة صريحة للعقود ذات النسخة في الاسم والمخطط القديم لمنع التخمين من اللاحقة.

## الاختبارات

- اختبار يفشل قبل الإصلاح ويثبت توجيه عقد التوقيت إلى `qararRpc` لا `qararRpcV2`.
- الإبقاء على اختبارات عقود `api_v2` الأخرى مثل التقويم والدعوات والموضوع المباشر.
- اختبار واجهة فتح الجلسة خارج الموعد يحمي المرحلة التالية وعدم الفتح قبل التأكيد.
