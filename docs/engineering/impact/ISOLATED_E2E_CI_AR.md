# عزل حزمة اختبارات المتصفح في CI

خريطة الأثر قبل التنفيذ: الحارس الحالي يطلب تصريحًا صريحًا وعنوانًا محليًا وحاوية qarar-e2e-* وقاعدة *_e2e؛ بينما CI يشغّل الإعداد العام postgres والحاويات العامة. لا نغيّر شروط الحارس ولا نعطي تصريحًا للتطوير أو الإنتاج. نولّد ملف إعداد مستقلًا من المثال المتعقب، مع مشروع وحاويات ووحدات تخزين ومنافذ loopback خاصة بالاختبار، ونفحص Compose المحلول قبل تشغيله أو إيقافه. لا نعدّل .env الموجود أو ترحيلات الأعمال.

الرحلة: إعداد CI ← توليد إعداد معزول والتحقق منه ← تشغيل Supabase وترحيلاته ثم البذر بعد Auth ← تشغيل Playwright وإعداد بيانات مؤسسة تجريبية ← تنظيف الحزمة نفسها. أي رفض قبل التشغيل لا ينشئ خدمة ولا يكتب بيانات. تنظيف بيانات المتصفح يبقى خاضعًا للحارس نفسه. تستمر الخدمات والمجلدات القديمة دون تغيير.

المستهلكون: workflow Dashboard Quality، Playwright config، fixture/global setup/global teardown واختبار الاجتماع؛ قارئ إعداد موحد يختار ملف الاختبار صراحة بدل خلطه بالإعداد المحلي. إعداد JWT يستخدم قاعدة الاتصال الفعلية بدل postgres الثابت؛ القيمة الافتراضية تبقى كما هي. لا تغيير API أو RPC أو صلاحيات المستخدمين أو حالات الأعمال أو الشاشات.

الاختبارات أولًا: إعادة إنتاج غياب تجهيز CI؛ رفض العنوان البعيد والحاويات/القاعدة/الوحدات/المنافذ غير المعزولة وعدم الكتابة عند الرفض؛ قبول إعداد الاختبار فقط؛ مقارنة Compose الافتراضي وعدم تداخل أسماء الموارد؛ تطبيق JWT على قاعدة مخصصة؛ تشغيل حزمة حقيقية ورحلات المتصفح إن سمحت موارد المضيف. توثّق الاختبارات المحجوبة منفصلة عن الناجحة. يلزم نجاح lint/الأنواع والحوكمة وفحوص العقود ذات الصلة. لا نشر أو تعديل للتطوير والإنتاج؛ الرجوع بإزالة إعداد CI الجديد، دون ترميم بيانات.

## التنفيذ والتحقق

- لم تتغير شروط assertIsolatedE2ETarget الأربعة. قارئ الإعداد الجديد يشترط ملفًا صريحًا ويطابق عنوان HTTP المخصص مع قاعدة SQL، ويمنع الرجوع الصامت إلى .env أو .env.example.
- ملف docker-compose.e2e.yml يعزل أسماء الخدمات الست عشرة ووحدات التخزين والمنافذ على loopback. إعداد المثال والـCompose العام لم يتغيرا؛ JWT وحده يستخدم اسم قاعدة الاتصال الفعلي مع اختبار توافق postgres داخل الحاوية المعزولة.
- المشغّل يرفض سياق Docker البعيد ومتغيرات تغيير وجهته، ويفحص نموذج Compose المحلول قبل التشغيل أو البذر أو الإيقاف؛ يرفض وحدات external والمجلدات المضيفة القابلة للكتابة. جامع سجلات Docker العام غير مشغّل ولا يُركّب مقبس المضيف في الحزمة. سجلات الفشل تُحجب منها الأسرار المولّدة.
- نجحت 6 اختبارات Node للعزل، و7 اختبارات Vitest للحارس وقراءة الإعداد، وفحص الأنواع وlint للملفات المعدلة والحوكمة والتوافق. اشتغلت صورة Supabase الفعلية من الصفر على qarar_e2e، ونجح اختبار JWT على qarar_e2e وpostgres داخل حاوية الاختبار نفسها.
- محاولة npm ci المحلية أُوقفت بسبب استهلاكها ذاكرة المضيف؛ المحاولة المحدودة للذاكرة اصطدمت بتنظيف مجلد تثبيت غير مكتمل. استُخدمت الاعتماديات المحلية القائمة للفحوص؛ لا يُعد ذلك إثباتًا لنجاح npm ci أو بوابة CI. لا تُغيّر الخدمات القائمة لتوفير الموارد.
- اكتملت الترحيلات محليًا. من 97 ملف قاعدة على qarar_e2e نجح 96 بعد جاهزية Auth؛ الملف 08 يتطلب cron.job غير المتاح على القاعدة المسماة خلاف postgres. لا نُنشئ جدولًا بديلًا أو نعدّل الاختبار لإخفائه. مجموعة قاعدة البيانات الكاملة واختبار التزامن نجحا في CI على الإعداد الافتراضي postgres. أُوقف تشغيل Vitest المحلي الأوسع لتخفيف موارد المضيف بعد نجاح المجموعة والبناء في CI؛ لا يُعد التشغيل المحلي الموقوف نجاحًا.
- التشغيل الأول 38828473496، للإيداع 779d394: نجحت quality وapi-contracts وdocker-smoke. فشلت خطوة Start Supabase المجمعة في مهمة المتصفح قبل تشغيل أي سيناريو، ولم تُتح صلاحية قراءة سجلاتها الكاملة عبر API العام. فُصلت مراحل التحقق والسحب والتشغيل وفحص JWT والبذر، وأضيفت رسالة تشخيص آمنة في check annotations بدل التخمين أو تعطيل الحارس. يلزم نجاح الإعادة قبل الدمج.
- أضيف تشغيل بوابة الجودة تلقائيًا عند الدفع إلى فروع codex/ci-* ليمكن التحقق قبل الدمج دون تغيير فرع العمل أو طلب صلاحيات API. أُزيلت حاويات الاختبار المحلية ووحداتها فقط بواسطة مشغّل التنظيف المحكوم؛ يمكن إعادة إنشائها بالسكربتات. لم يُمس التطوير أو الإنتاج.
- الإعادة 38830213861، للإيداع ae57c28: نجحت البوابات الثلاث مجددًا. أثبت التشخيص أن السحب الثاني يفشل عند analytics برسالة `toomanyrequests: Data limit exceeded`، قبل تشغيل قاعدة الاختبار. خريطة الإصلاح قبل التنفيذ: تُشغّل رحلة المتصفح بعد فحص القاعدة على العامل نفسه لإعادة استخدام الصور التي سُحبت أصلًا، بعد إزالة حزمة postgres المؤقتة بالكامل. إعداد E2E وقاعدته وملفه وحارسه لا تتغير. لا تخزين صور ضخم أو مرايا بديلة أو صلاحية سجل إضافية. يبقى اسم regulations-e2e بوابة تجميع تعتمد على نجاح مجموعة القاعدة والمتصفح والجودة والعقود؛ لا تُحذف أي مواصفة أو تقلّل تأكيداتها. تُفحص الصور محليًا قبل التشغيل بـ pull never، ويجب أن تفشل الرحلة إن كانت صورة ناقصة. يلزم اختبار هذه البنية في CI قبل الدمج.
- التشغيل 38831613070 للإيداع a378896 أثبت نجاح الحزمة المعزولة وJWT والبذر ووصول Playwright إلى الواجهات. الفشل التالي في المواصفات: اللوائح تطلب العنوان والمعالج القديمين، واختبار الاجتماع يستهلك 240 ثانية ثم يحجب خطأ إغلاق السياق موضع التعطل الأصلي. خريطة الدفعة التالية قبل التعديل: مواصفة اللوائح تتبع المكتبة الحالية وتتحقق من المرجع والمسودة التلقائيين وحفظ أول بند وإعادة القراءة، دون إدخال رمز أو تخفيف التحقق. مواصفة الاجتماع تحفظ أول خطأ عند التنظيف، وتضع مهلًا على الأفعال والطلبات وخطوات مسماة لـRPC، وتقرأ المشاركة من الحلقة التي حلت محل اللوحة المكررة في #138. السياقات المنشأة يدويًا يجب أن ترث إعداد الهاتف فعلًا، لا أن تختبر سطح المكتب تحت اسم مشروع الهاتف. لا تغيير في واجهة أو عقد أو صلاحية أو انتقال حالة تجاري، ولا حذف للرحلة أو التوقيع أو التصويت. اختبار مساعد التنظيف يفشل قبل الإصلاح ثم يحمي الخطأ الأصلي وفشل التنظيف المستقل.

## إعادة التشغيل على عامل CI نظيف

## جمع دفعات 139–148 وإصلاح نتائج المتصفح (16 أكتوبر)

قبل التعديل: جُلب فرع العمل البعيد عند 2337200، وفيه الدفعات الجديدة مدموجة بالفعل؛ جُمعت في فرع الاختبار المعزول، لا في مجلد التطوير المشغّل. التعارض الوحيد نص تاريخ ملف الاستكمال، وحُفظ محتوى الفريقين. نتيجة CI السابق: 13 ناجحة و5 فاشلة؛ مكتبة اللوائح والهاتف للاجتماع نجحا، لكن شريط التحكم المكتبي يحجب زر إنهاء المناقشة بسبب صفّين بعرض أدنى أكبر من عمود الطاولة.

خريطة الإصلاح: شريط الرئيس يبقى تحت الطاولة بالقيم والمكونات نفسها، لكن مجموعتي الإجراءات تتكدسان ضمن عرض العمود بدل فرض صف مكتبي لا يتسع. لا تغيير في صلاحية أو انتقال أو RPC أو سجل قائم؛ الفشل السابق في locator.click هو اختبار الانحدار، ويجب أن ينجح النقر العادي دون force أو dispatchEvent مع غياب تمرير أفقي. المرحلة السابقة المناقشة، والتالية التصويت والقرار والمحضر تبقى في الرحلة متعددة الحسابات.

الفشلان الآخران في تجهيز الاختبار: نموذج تقديم الموضوع يستدعي prepare ثم رفع المرفقات ثم submit، بينما mock قديم يعيد نتيجة submit إلى prepare، فيرفضها النموذج بحق. نطابق المرحلتين ونؤكد ترتيب الطلبات وتطابق receipt وعدم استدعاء العقود القديمة. اختبار المستخدمين يفترض العدد 32 رغم إنشاء اختبار الاجتماع هويات أخرى في المؤسسة التجريبية؛ نقرأ العدد المتوقع من SQL داخل الهدف المعزول المحروس ونقارنه بالواجهة، مع بقاء التحقق من صفحة ثانية والبحث خارج الأولى وفشل الشبكة. لا نغيّر count في التطبيق ولا نتجاوز MFA أو العزل.

نطاق التحقق المجمّع يشمل الاختبارات الجديدة 99–107، والجودة والعقود والتزامن ورحلات المتصفح على الهاتف والمكتب. لا تُعدّ إضافات الفريق مجرّبة تشغيليًا قبل اكتمال المجموعة، ولا إعادة نشر أو تغيير بيانات التطوير أو الإنتاج.

1. `sh scripts/prepare-e2e-supabase-env.sh` (يشترط CI=true؛ ينشئ .env.e2e بصلاحيات 0600، ولا يستبدل ملفًا موجودًا).
2. `node scripts/e2e-supabase.mjs config` ثم `pull` ثم `up`.
3. `node scripts/test-e2e-jwt-database.mjs` ثم `node scripts/e2e-supabase.mjs seed`؛ البذر بعد اكتمال خدمة Auth كما كان.
4. Playwright يقرأ المسار QARAR_E2E_ENV_FILE الذي كتبته خطوة التجهيز في GITHUB_ENV. شغّل `npm run test:e2e` داخل apps/dashboard.
5. عند الفشل: `node scripts/e2e-supabase.mjs logs`. التنظيف: `node scripts/e2e-supabase.mjs down`، ويزيل حزمة الاختبار ووحداتها فقط بعد فحص العزل مجددًا.
