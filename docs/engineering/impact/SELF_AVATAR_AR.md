# الصورة الشخصية — تحليل أثر قبل التنفيذ

المستخدم النشط يدير صورته وحده دون صلاحية IAM، ودون اختيار مستخدم مستهدف.
السابق: الدخول وسياق المؤسسة؛ المعدل: رفع/استبدال/إزالة الصورة؛ التالي:
عرضها في حسابي والشريط ثم استمرارها بعد الدخول مجددًا. لا تغيير لحالة
الهوية أو الأدوار أو كلمة المرور أو عضويات المجلس.

جدول خاص في IAM يحتفظ بنسخة JPEG مصغرة فقط، لا بالأصل أو بيانات EXIF.
الصورة صغيرة ومحدودة الحجم، وتقرأ عبر RPC سياقي ومسار خاص no-store؛ لا
روابط عامة ولا service-role يتجاوز صلاحية صاحب الحساب. السجلات القديمة
بلا صورة تظل صحيحة. رقم مراجعة يمنع استبدالًا متزامنًا بصمت، والقفل يحمي
التحديث والتدقيق في معاملة واحدة. يبقى صف خالٍ عند الإزالة لحفظ المراجعة.
الأصل لا يخزن؛ الفشل يبقي الصورة السابقة. سجل التدقيق لا يحمل الصورة.

المستهلكون: صفحة حسابي، SelfAvatar المشترك، AppShell، API account/avatar،
عقدا api_v2 جديدان وregistry، جدول IAM وصلاحيات executors. لا وظائف
دورية أو إشعارات أو محاضر متأثرة. no-store ومنع user_id يحميان تبديل الحساب.

واجهة حسابي تُرحّل إلى tokens وButton/Card/InlineMessage. أي مكون صورة
مشترك جديد يُختبر وتضاف قصته. الفحص: PNG/JPEG صحيحتان، ملف مزيف/SVG، الحجم
والأبعاد، رفض جلسة/دور غير نشط، مستخدم مؤسسة أخرى، تعارض وتكرار وفشل خادم،
تدقيق وعدم كشف الصورة لمستخدم آخر، استمرار الصورة وإزالتها، 1440 و390px.
ترحيل جديد فقط على DEV؛ لا تعديل لترحيل مطبق ولا نشر إنتاجي. الإصلاح
الأمامي يعطل إجراءات الرفع دون تغيير البيانات القديمة عند تعذر الإطلاق.

## العقود

`get_my_avatar_v2(p_include_content boolean=false)` يعيد revision وhas_image
وcontent_base64 (فارغ افتراضيًا). لا يقبل معرف مستخدم أو مؤسسة.
`set_my_avatar_v2(p_content_base64 text,p_expected_revision integer,p_request_id uuid)`
يعيد saved/revision/has_image؛ null يزيل الصورة. إعادة الطلب الأخير نفسه
آمنة، والنسخة القديمة ترفض PT409. كلا العقدين للمستخدم النشط الحالي فقط.
لا حقول صورة في get_my_account أو access-context، لتجنب تحميل الصورة في
كل رحلة. API القراءة لا يخزن مؤقتًا ولا يقرأ path أو user_id من العميل.

المعالجة باستخدام sharp بنفس النسخة 0.35.3 الموجودة مع Next، مع التصريح
بها كاعتماد مباشر دون ترقية؛ الأصل محدود إلى 2MiB و16 مليون بكسل، والنسخة
JPEG إلى 512×512 و512KiB كحد أعلى. تدقيق npm كشف تنبيهات اعتماديات قائمة؛
لا ترقية شاملة أو npm audit fix --force ضمن تغيير الصورة.

اختبار المتصفح أعاد إنتاج تعارض حقيقي بعد إزالة من نافذة أخرى: كود 40001
المبدئي تسبب في رد 504 بعد انتظار 60 ثانية على مسار HTTP، رغم رفضه الفوري
في اختبار SQL. نستخدم PT409 للتعارض التجاري الصريح بدل رمز rollback.
أضيف ترحيل تصحيحي مستقل لأن الأول طُبق بالفعل، ولا تُغيّر العقود الأخرى.
يحمي الاختبار الواقعي إظهار التعارض وإعادة القراءة قبل إعادة الحفظ.

## نتائج التحقق

اجتاز الاختبار الحقيقي على devqarar رحلة مستخدم عادي بلا دور إداري:
حفظ الاسم، رفع الصورة واستمرارها، تطبيع JPEG، رفض ملف مزيف، تعارض نافذتين
وإعادة القراءة، إزالة الصورة وتدقيق أربع عمليات، وعرض 1440 و390 دون تجاوز
أفقي. تغيير كلمة المرور نجح مع رفض الحالية الخاطئة، إنهاء جلسة المتصفح،
قبول الجديدة ورفض القديمة. أُعيد الاختبار بعد محاولة سابقة لم تؤكد نجاح
كلمة المرور؛ التتبع الأخير أكد طلبين فقط: رفض ثم نجاح، دون تغيير عقدها.

نجح البناء، و40 اختبارًا مركّزًا، و16 اختبار قاعدة بيانات، وبوابة حوكمة
التطوير وترميز الوثائق. عقود DEV تطابق 227 عقدًا وسجل الترحيلات يطابق 267
ملفًا وبصماتها. لا نشر إنتاجي. فحص العقود يجب تشغيله مع
DB_CONTAINER=qarar-dev-supabase-db؛ الافتراضي يتصل بقاعدة متأخرة عن DEV.
نجح typecheck وlint (التحذيرات الستة السابقة فقط) وبناء Storybook، مع قصة
SelfAvatar للوضعين الفاتح والداكن. طُبقت معايير التصميم المركزية على واجهة
الحساب ومكون الصورة؛ لا يُدّعى اكتمال ترحيل جميع واجهات النظام القديمة.
