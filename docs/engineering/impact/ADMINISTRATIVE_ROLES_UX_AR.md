# إدارة الأدوار للإداري دون تفاصيل تقنية

## القاعدة وخريطة الأثر قبل التنفيذ

المشكلة: شاشة الإدارة تعرض إنشاء صلاحية بكتابة الموديول والرمز والإجراء،
وتطلب رمز الدور وتعرض الرموز في المصفوفة. هذه ليست رحلة الإداري.
البديل: اختيار دور، قراءة قدراته مجمعة، تعديل اختياراته، ثم مراجعة ملخص
الإضافات والسحب وإرسال طلب وفق سياسة الاعتماد الحالية. لا تغيير لهذه السياسة.

- السابقة: دخول إداري مخول وقراءة الأدوار ودليل الصلاحيات.
- المعدلة: العرض والبحث وإنشاء/تعديل بيانات الدور وتحديد الصلاحيات.
- التالية: طلب اعتماد ثم تطبيق بواسطة مسؤول آخر، وبعده إدارة عضوية المستخدم.
- الحالة: اختيارات محلية لا تؤثر في الصلاحيات الفعلية؛ الإرسال ينشئ طلبًا
  معلّقًا فقط. فشل القراءة يمنع التحرير؛ فشل اتصال mutation غير المؤكد يمنع
  إعادة الإرسال حتى إعادة القراءة والتحقق من قائمة الطلبات.
- المستهلكون: صفحة admin/permissions، PermissionMatrix، API admin/iam؛
  توليد رمز الإنشاء داخل admin/iam. API admin/roles القديم غير مستخدم في
  الشاشة الجديدة، ويحافظ على عقد مستهلكيه دون تغيير.
- العقود: admin_list_roles، admin_list_permissions، admin_get_role_detail،
  admin_upsert_role، admin_deactivate_role، admin_request_role_permissions_change.
  تبقى حدود المؤسسة وMFA والتحقق من الصلاحية داخل RPC القائمة.
- الجداول: roles/permissions/role_permissions/iam_change_requests والتدقيق القائم؛
  لا ترحيل مخطط ولا تعديل عضويات أو كلمات مرور أو نطاقات تقديم ولا منح تلقائي.
- الوظائف المجدولة والمحاضر: غير متأثرة.
- القديم: الرموز الثابتة لا تتغير. تعديل بيانات الدور لا ينشط الدور المعطل
  ضمنيًا؛ إعادة التفعيل فعل صريح. إنشاء الدور يستخدم رمزًا خادميًا UUID.
- الصلاحيات الناقصة في التطوير ليست مهمة إدخال للإداري. لا نضيفها تلقائيًا
  تنفيذًا لطلب المستخدم السابق؛ يظهر تنبيه نقص التهيئة ولا نختلق خيارات فعالة.
- الأدوار: القارئ يرى فقط؛ مدير الأدوار يعدل البيانات؛ مدير الصلاحيات يرسل
  المصفوفة؛ لا تكفي أي منها لمنح إدارة النظام أو تجاوز سياق المجلس.

## الاختبارات والإصدار

اختبار فاشل أولًا لاختفاء الحقول والرموز، إنشاء الاسم دون رمز، مجموعات عربية،
ملخص إضافات/سحب، تحميل وفشل قراءة، منع قارئ من التعديل، تعارض/فشل يحفظ المدخلات،
ومنع حذف اختيارات عند تغيير الدور دون تأكيد. اختبار API يثبت توليد الرمز
وحفظ رمز السجل القديم ورفض أسماء/نطاقات غير صالحة واختبارات رفض RPC.
تشغيل الأنواع وlint والاختبارات المركزة والبناء وبوابة حوكمة التطوير.
فحص مرئي بعرض 1440 و390، بالوضعين في بيئة معزولة دون منح حسابات فعلية.
لا دمج فروع المطور الآخر ولا نشر إنتاج. الرجوع بإعادة الواجهات فقط، والعقود
والسجلات التاريخية تظل سليمة.

## خلل كشفه الاختبار المتكامل

اعتماد الطلب يكتب حالة applied والصلاحيات بنجاح، لكن RPC يرجع HTTP 204
لعقد void. كان qararRpc يحاول تحليل جسم فارغ كـ JSON، فيظهر فشل كاذب
وقد يشجع تكرار عملية نُفذت. الإصلاح في ناقل RPC المشترك: 204 فقط يرجع null،
ولا تُخفى استجابة JSON تالفة أو خطأ HTTP. يشمل الناقلين V1 وV2 ومستعملي
الأوامر void مثل الاعتماد. لا تغيير لقاعدة البيانات أو سياسات الاعتماد.
أُعيد إنتاجه عبر HTTP/متصفح، وكتب اختبار فاشل أولًا للناقل ونجاح الاعتماد
والرفض الذاتي، مع اختبار مجاور يبقي JSON التالف خطأ.

## التحقق الفعلي

- 18 اختبارًا مركزًا ناجحًا للواجهة، API، الحقول المشتركة وناقل RPC.
- رحلة متصفح وHTTP ناجحة على التطوير بمؤسسة وحسابات اختبار معزولة:
  إنشاء الدور، طلب الصلاحيات دون منح مبكر، رفض الاعتماد الذاتي، اعتماد
  مسؤول ثانٍ، منع غير المخول، تعطيل الدور وإعادة تفعيله.
- تحقق قاعدة البيانات داخل معاملة تُلغى: صلاحية في نطاق العضوية فقط؛
  رفض نطاق آخر أو النطاق العام أو إدارة المستخدمين، ورفض العضوية المنتهية.
- فحص مرئي بعرض 1440 و390 في الفاتح والداكن، بلا تمرير أفقي؛ أزيل شريط
  ثابت كان يغطي المحتوى على الهاتف. الصور محفوظة ضمن /tmp/qarar-roles-*.
- حسابات الاختبار تُحظر بعد الاختبار، مع الاحتفاظ بسجلها للتدقيق. لم تتغير
  بيانات أو صلاحيات أي حساب فعلي، ولم يُكتب في الإنتاج.
- الحزمة الكاملة للواجهة: 401 اختبار ناجح في 94 ملفًا. الأنواع والبناء
  وlint وبوابة حوكمة التطوير وgit diff --check ناجحة؛ lint يحتفظ بستة
  تحذيرات سابقة خارج الملفات المعدلة في هذه المهمة، دون أخطاء.
