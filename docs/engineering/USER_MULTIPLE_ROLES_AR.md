# إدارة أدوار المستخدم المتعددة — خريطة الأثر قبل التنفيذ

## الرحلة والثابت

إنشاء الهوية بدعوة/كلمة مؤقتة ← أدوار متعددة اختيارية ← جهة العمل ونطاق
التقديم ← تفعيل الهوية/استبدال الكلمة ← تقديم ضمن النطاق. يمكن أيضًا فتح
الأدوار من عمليات مستخدم سابق. لا يؤدي حفظ الأدوار إلى تفعيل حساب أو إعفاء
من استبدال الكلمة أو تغيير `is_system_admin`. التقديم متعدد المجالس مستقل
عن العضوية والتصويت؛ هذه الدفعة لا تضيف دور مقدم وهميًا إلى مجلس.

## العقود والمستهلكون المثبتون

- `memberships`: دور ووحدة وسريان و`active/inactive/ended`؛ قيود المؤسسة
  والفترة والازدواجية موجودة. المشغلات الحالية تحفظ التدقيق وتمنع قيادة
  مزدوجة وتفرض حدود IAM؛ لن تُضعف أو تُحذف.
- `admin_get_user_detail` يقرأ العضويات التاريخية؛ `admin_assign_role`
  يقبل النشط فقط. تحتاج الحسابات المدعوة إدارة أدوار قبل تفعيلها دون
  تزوير حالة `active` للمستخدم. عقدان جديدان في api_v2 بدل تعديل القديم.
- القراءة الجديدة توفر العضويات وupdated_at لكل سجل والخيارات النشطة
  من أدوار ووحدات المؤسسة، مع حفظ عرض الربط التاريخي غير المتاح.
- الحفظ الجديد مدير نظام فقط، تغيير واحد محدد الهوية أو إضافة. قفل
  `lock_iam_authority_boundary` قبل قفل المستخدم/العضوية لمنع عكس ترتيب
  الأقفال. سجل سابق يتطلب updated_at المتوقع؛ تعارض يرفض دون تغيير.
  الإضافة UUID يُولد في DB، وطلب تكرار يحمل UUID داخليًا لا يطلب من المستخدم.
  التحقق أن العضوية تخص المستخدم والمسار والمؤسسة، وأن الدور والوحدة نشطان
  عند منح/تغيير صلاحية. تعطيل غير نشط يبقي التاريخ؛ ended لا يعاد تفعيله.
- API `/api/admin/users/[userId]/roles`: session/MFA وorigin/body guards؛
  لا service-role ولا هدف جسم العميل. رد مأمون مع traceId وسبب داخلي مدقق.
- UI: مكون داخل نافذة الإنشاء بعد إيصال الحساب، ثم نطاق التقديم؛ صفحة
  من عمليات المستخدم، لا يعيد فشل الأدوار إنشاء Auth أو إرسال دعوة ثانية.
- المستهلكون التاليون: سياق الصلاحيات، العضويات، قيادة المجلس، MFA،
  التصويت، تقديم الموضوع. لا تغيير دوال استحقاقهم ولا البيانات القديمة.
- آخر مدير محمي: هذه العملية لا تعدل flag إدارة النظام أو حالة الحساب.
  الأدوار المرتفعة قابلة للتعديل من مدير النظام فقط وفق trigger السابق.
- لا jobs أو إشعارات جديدة؛ audit_row_change محفوظ مع حدث صريح للمستخدم
  الحقيقي. ترحيل أمامي على قاعدة التطوير فقط، بلا تعديل ترحيلات مطبقة.

## الاختبارات والرجوع

اختبار فاشل قبل الكود: دوران لمستخدم مدعو دون تفعيله؛ تعطيل/إعادة تفعيل؛
تعديل مع تعارض؛ عضوية مستخدم آخر/مؤسسة أخرى؛ منع العادي؛ قيد التكرار
والقيادة؛ صلاحيات قبل/بعد التعطيل؛ الحفاظ على مدير النظام والكلمة المؤقتة.
واجهة: تحميل/فشل/نجاح/منع النقر المزدوج ومدخلات محفوظة، مكون الإنشاء
السابق والنطاق التالي؛ desktop/mobile. lint/typecheck/governance والعقود
المجاورة 06/44/83/84. الإصلاح الأمامي فقط عند عيب، دون حذف تاريخ الأدوار.

## تصحيح مثبت أثناء اختبار DB

قفل CORE بواسطة FOR SHARE يحتاج UPDATE غير ممنوح لـIAM؛ لا نوسع صلاحياته.
نستعمل قفل الهيكل التنظيمي المشترك الموجود للعمليات التنظيمية، مع قراءة
CORE فقط. مشغل set_updated_at يستعمل now داخل المعاملة نفسها، لذلك نضيف
مشغلًا تالياً لأدوار المستخدم يجعل نسخة التحديث clock_timestamp، دون تغيير
توقيع أي عقد. مستهلكو updated_at (قيادة وعضوية المجلس وإدارة الأدوار) يقارنون
النسخة لا وقت المعاملة؛ جميعهم يظلون متوافقين وتختبر عقودهم مجددًا.

## التحقق المنفذ وحدود الدفعة

- اختبار DB 85: اثنتان وعشرون حالة؛ إضافة دورين للحساب غير النشط دون
  تفعيله، تعديل، تعطيل وإعادة تفعيل، إعادة إرسال آمنة، منع ازدواج الفترة
  والتعارض والهدف الآخر والعادي، وسحب الصلاحية السياقية بعد التعطيل.
- العقود المجاورة 06/44/65/83/84 أُعيد تشغيلها على قاعدة التطوير.
- رحلة المتصفح المعزولة: إنشاء حقيقي بكلمة مؤقتة، إضافة دورين، تعديل
  الصفة، تعطيل وإعادة تفعيل، حفظ نطاق التقديم، ثم استبدال الكلمة والدخول
  بالجديدة ورفض القديمة والعادي عن API الأدوار. نجحت؛ صور 1440/390 فُحصت
  دون تجاوز أفقي. هويات الاختبار فقط عُطلت في Auth، والتاريخ محفوظ.
- typecheck ناجح؛ lint دون أخطاء وستة تحذيرات سابقة؛ فحوص الواجهة/API
  والإنشاء ونطاق التقديم ناجحة؛ development-governance ناجح.
- ترحيلان أماميان مطبقان في التطوير فقط. لا دمج أو نشر إنتاجي.
- المتبقي في إدارة المستخدمين: دور مقدم صريح وإكمال ربط خيارات التقديم
  بتصنيف الموضوع، ورفع الصورة الشخصية. لا تدعي هذه الدفعة إكمالهما.
