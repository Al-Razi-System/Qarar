## Issue 01

**Title:** `PB-001: بناء شاشة ونموذج إنشاء موضوع جديد`  
**Prerequisite:** `PB-059` / `FR-00-10`<br>
**Feature Request:** `FR-01-01`<br>
**Dependencies:** `PB-043`, `PB-045`, `PB-047`
**Backlog ID:** `PB-001`  
**Priority:** `High`  
**Owner:** `Flutter`  
**Area:** `Flutter`  
**Sprint:** `Sprint 01 - Core Topic Flow`  
**Release:** `Release 1`  
**Labels:** `flutter`, `enhancement`

### Feature Request Detail

**المشكلة والقيمة:** يحتاج مقدم الموضوع إلى نقطة دخول رسمية تحفظ موضوعاً قابلاً للتتبع داخل مؤسسته، لا مجرد نموذج واجهة يمكن تجاوزه أو فقد بياناته.  
**المستخدم والنتيجة:** ينشئ المستخدم المخول موضوعاً من مسار محمي، فيحصل على رقم مرجعي وحالة بداية ومسار واضح، ويصبح قابلاً للمراجعة وفق الصلاحيات.  
**قواعد العمل:** تستخدم الحقول والقيم المرجعية من `PB-043`؛ يفرض الخلفي المؤسسة والجهة المالكة وهوية المنشئ؛ ويسجل الإنشاء في `Audit Trail`. لا تكون حراسة الواجهة بديلاً عن `RLS`.

### Goal

تمكين المستخدم المخول من إدخال موضوع جديد عبر شاشة ونموذج واضحين يمثلان نقطة الدخول الرسمية إلى المسار الحوكمي.

### Scope

- إنشاء شاشة أو صفحة إنشاء موضوع جديد
- بناء نموذج إدخال أولي للحقول الأساسية
- دعم إدخال عنوان الموضوع وبياناته الأولية الرئيسية
- حفظ الموضوع في الخلفية ضمن المؤسسة والسياق المصرح بهما
- إنشاء رقم مرجعي وحالة بداية وسجل إنشاء قابل للتتبع
- مراعاة الاتجاه العربي وتجربة استخدام مناسبة للنواة

### Out of Scope

- التحقق المعمق من جميع قواعد الإدخال
- مسارات المراجعة أو الإرجاع أو الرفض
- دعم إعدادات مرجعية متقدمة خارج الحقول الأساسية

### Acceptance Criteria

1. توجد شاشة أو صفحة واضحة لإنشاء موضوع جديد.
2. يحتوي النموذج على الحقول الأساسية المتوقعة في هذه المرحلة.
3. تكون الواجهة قابلة للاستخدام بالعربية و`RTL`.
4. يحفظ النظام الموضوع ضمن المؤسسة الصحيحة مع رقم مرجعي وحالة بداية وهوية المنشئ.
5. يسجل إنشاء الموضوع في `Audit Trail`، ولا يسمح طلب خلفي مباشر بإنشاء موضوع خارج صلاحية المستخدم.

## Issue 02

**Title:** `PB-002: تطبيق التحقق من الحقول الإلزامية وقواعد الإدخال الأساسية`  
**Feature Request:** `FR-01-02`<br>
**Dependencies:** `PB-001`
**Backlog ID:** `PB-002`  
**Priority:** `High`  
**Owner:** `Flutter`  
**Area:** `Flutter`  
**Sprint:** `Sprint 01 - Core Topic Flow`  
**Release:** `Release 1`  
**Labels:** `flutter`, `qa`

### Feature Request Detail

**المشكلة والقيمة:** التحقق في الواجهة فقط يمكن تجاوزه، والتحقق الخلفي فقط يضعف تجربة الاستخدام. المطلوب قواعد موحدة تمنع البيانات غير الصالحة مع رسائل عربية واضحة.  
**المستخدم والنتيجة:** يرى مقدم الموضوع الخطأ بجانب الحقل قبل الإرسال، بينما يرفض الخلفي أيضاً أي طلب غير صالح يصل مباشرة.  
**قواعد العمل:** تشمل القواعد الحقول الإلزامية والقيم المرجعية والشكل والطول؛ لا تظهر للمستخدم رسائل تقنية أو تفاصيل سياسات الوصول؛ ولا ينشأ سجل جزئي عند فشل التحقق.

### Goal

منع إدخال موضوع ناقص أو غير صالح عبر فرض الحد الأدنى من قواعد التحقق على النموذج الأساسي.

### Scope

- تطبيق التحقق على الحقول الإلزامية
- عرض رسائل واضحة عند نقص البيانات
- منع الاستمرار في الحفظ النهائي عند غياب المتطلبات الأساسية
- توحيد سلوك التحقق مع ما ورد في `US-01`
- إعداد القاعدة التي ستستخدم لاحقاً في اختبارات القبول

### Out of Scope

- قواعد تحقق متقدمة جداً خاصة بكل نوع موضوع
- محرك سياسات ديناميكي للإدخال
- معالجة شاملة لجميع حالات المسودة المتقدمة

### Acceptance Criteria

1. لا يسمح النظام بالحفظ النهائي عند غياب الحقول الإلزامية الأساسية.
2. تظهر رسائل تحقق واضحة ومفهومة للمستخدم.
3. يكون سلوك التحقق متسقاً مع معايير القبول في `US-01`.
4. لا يكسر التحقق تجربة إدخال الموضوع أو اتجاه الواجهة العربية.

## Issue 03

**Title:** `PB-003: بناء قائمة مراجعة الموضوعات للمراجعين`  
**Feature Request:** `FR-01-03`<br>
**Dependencies:** `PB-001`, `PB-045`
**Backlog ID:** `PB-003`  
**Priority:** `High`  
**Owner:** `Flutter`  
**Area:** `Flutter`  
**Sprint:** `Sprint 01 - Core Topic Flow`  
**Release:** `Release 1`  
**Labels:** `flutter`, `enhancement`

### Feature Request Detail

**المشكلة والقيمة:** يحتاج المراجع إلى قائمة عمل صحيحة ضمن نطاقه، لا إلى كشف جميع موضوعات المؤسسة أو موضوعات مؤسسات أخرى.  
**المستخدم والنتيجة:** يرى المراجع المخول موضوعاته ذات الصلة فقط، مع الرقم المرجعي والعنوان والنوع والأولوية والحالة والجهة المالكة، ثم يفتح الموضوع للمراجعة.  
**قواعد العمل:** تصفية النطاق تنفذ في الخلفية وفق الدور والسياق المؤسسي؛ لا يكفي إخفاء العناصر في الواجهة؛ ولا تظهر تفاصيل حساسة غير لازمة لبطاقة المراجعة.

### Goal

توفير قائمة تشغيلية تمكّن المراجع من رؤية الموضوعات الداخلة ضمن نطاقه والبدء في مراجعتها.

### Scope

- إنشاء قائمة أو عرض أولي للموضوعات المرسلة للمراجعة
- إظهار البيانات الأساسية الكافية لتمييز الموضوع
- دعم فتح الموضوع من القائمة
- تهيئة العرض ليخدم المراجعة التشغيلية اللاحقة
- مراعاة أن تكون القائمة قابلة للتصفية أو التوسعة لاحقاً

### Out of Scope

- منظومة بحث وتصفية متقدمة
- لوحات تشغيلية تحليلية
- إجراءات الاعتماد أو الرفض نفسها داخل هذا العنصر

### Acceptance Criteria

1. توجد قائمة مراجعة يمكن للمراجع استخدامها لرؤية الموضوعات ذات الصلة.
2. تعرض القائمة الحد الأدنى من البيانات اللازمة لفهم كل موضوع.
3. يمكن الانتقال من القائمة إلى عرض الموضوع أو فتحه للمراجعة.
4. تكون البنية قابلة لدعم إجراءات `PB-004` لاحقاً دون إعادة تصميم كبيرة.

## Issue 04

**Title:** `PB-004: تنفيذ إجراءات اعتماد وإرجاع ورفض وتأجيل الموضوع`  
**Feature Request:** `FR-01-04`<br>
**Dependencies:** `PB-002`, `PB-003`, `PB-045`, `PB-047`
**Backlog ID:** `PB-004`  
**Priority:** `High`  
**Owner:** `Supabase / Integration`  
**Area:** `Integration`  
**Sprint:** `Sprint 01 - Core Topic Flow`  
**Release:** `Release 1`  
**Labels:** `supabase`, `integration`, `security`

### Feature Request Detail

**المشكلة والقيمة:** إجراء مراجعة غير محكوم قد يغير حالة الموضوع بلا مساءلة. المطلوب انتقال حالة ذري ومدقق يطبق في الخلفية ويهيئ الموضوع للمرحلة التالية الصحيحة.  
**المستخدم والنتيجة:** يختار المراجع المخول إجراء الاعتماد أو الإرجاع أو الرفض أو التأجيل؛ يتحقق النظام من الحالة والصلاحية، ثم يحفظ النتيجة والسبب والأثر التدقيقي معاً.  
**قواعد العمل:** تحدد `PB-043` أسماء الحالات والانتقالات المسموحة؛ يلزم سبب للإرجاع والرفض؛ يرفض النظام الإجراء المكرر أو المنفذ على حالة تغيرت؛ ولا يعد اعتماد الموضوع اعتماداً نهائياً لقرار أو محضر.

### Goal

تمكين المراجع المخول من اتخاذ الإجراء الأولي الصحيح على الموضوع بحيث ينتقل إلى الحالة المناسبة وفق السياسة.

### Scope

- دعم إجراءات اعتماد الموضوع أو إرجاعه أو رفضه أو تأجيله
- تحديث حالة الموضوع وفق الإجراء المختار
- تسجيل الملاحظات أو الأسباب عند الحاجة
- فرض الصلاحيات المرتبطة بأفعال المراجعة
- ربط الإجراء بالسجل التدقيقي عند الحاجة
- معالجة تعارض التحديث بإعادة تحميل الحالة بدلاً من تنفيذ انتقال غير صالح

### Out of Scope

- الإحالة بين الوحدات الحوكمية
- انتقالات موضوع متقدمة خارج المراجعة الأولية
- تكاملات إشعار موسعة إذا لم تكن لازمة في هذه المرحلة
- سياسات استثنائية معقدة متعددة المستويات

### Acceptance Criteria

1. يستطيع المراجع المخول تنفيذ إجراءات الاعتماد أو الإرجاع أو الرفض أو التأجيل.
2. تتغير حالة الموضوع بشكل صحيح بعد كل إجراء.
3. يسجل سبب الرفض أو الإرجاع عند استخدامه.
4. لا يستطيع مستخدم غير مخول أو من مؤسسة أخرى تنفيذ أفعال المراجعة الحساسة، حتى بطلب مباشر للخلفية.
5. يحدث الموضوع وسجل انتقال الحالة والأثر التدقيقي ضمن عملية متسقة واحدة.
