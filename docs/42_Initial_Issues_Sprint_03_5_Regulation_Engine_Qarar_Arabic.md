## 1. سبب السبرنت

اكتمل في `Sprint 03` إنشاء الموضوعات والحضور والنصاب والتصويت، لكن المسار لا يزال قابلاً للعمل من دون أن يكون مصدره لائحة أو بنداً يحدد المجلس والجهات والأدوار. هذا يمنع `Qarar` من إثبات الامتثال ويجعل الانتقال إلى المحاضر والقرارات سابقاً لأوانه.

هذا السبرنت لا يعيد بناء الحضور أو التصويت. يضيف طبقة القرار اللائحي، ويربطها بالتدفق الموجود، ويثبت النسخة والقواعد التي حكمت كل موضوع.

## 2. النتيجة المستهدفة

`موضوع -> بند لائحي -> مجلس/جهات/أدوار -> قالب مسار -> انتقالات مسموحة -> موضوع قابل للمراجعة والاجتماع -> أثر لائحي وتقارير امتثال`

إذا لم تنطبق لائحة، يجب أن ينشأ مسار مخصص أو استثنائي موثق ومصرح به، لا أن يستمر الموضوع بمسار افتراضي غير معروف المصدر.

## 3. قواعد حاكمة

- اللائحة وإصدارها وبندها ومسارها كيانات مستقلة قابلة للتدقيق.
- لا تستخدم لائحة غير سارية لإنشاء مسار جديد.
- لا يغير تحديث اللائحة بأثر رجعي مسار موضوع بدأ سابقاً؛ تحفظ نسخة مطبقة على الموضوع.
- يفضل المسار اللائحي عند انطباقه، ولا يسمح بالاستثناء بلا سبب وصلاحية وأثر.
- لا تعتمد حماية Flutter وحدها؛ يفرض المحرك والسياسات الخلفية القرار نفسه.
- المحرك حتمي وقابل للتفسير؛ لا توجد لغة شيفرة ينفذها المستخدم داخل اللائحة في `MVP`.

## 4. ترتيب التنفيذ والتوازي

`PB-060` -> `PB-061` و`PB-062` -> `PB-063` -> `PB-064` -> `PB-065` و`PB-066` -> `PB-067` -> `PB-068` -> `PB-069`.

يمكن لعضوين العمل بالتوازي على `PB-061` و`PB-062` بعد اعتماد النموذج، بينما يثبت العضو الثالث عقد المسار والاختبارات. لا يبدأ `PB-064` قبل وجود بيانات اختبار حقيقية لثلاثة مجالس وبنود متعددة.

## Issue 01 - PB-060

**Title:** `PB-060: تأسيس نموذج محرك اللوائح والبنود والإصدارات`  
**Feature Request:** `FR-03.5-01`  
**Owner:** `Supabase / Integration`

### Goal
